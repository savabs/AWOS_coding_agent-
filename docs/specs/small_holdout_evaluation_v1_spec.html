Spec: Small Holdout Evaluation v1

phase/1 · topic/evaluation · active · 2026-07-30

Goal

Run one real-orchestrator evaluation trial on one small private task with bounded storage, evaluator-owned acceptance, and an auditable report.

Governing research: small_holdout_evaluation_v1.html
Task: small_holdout_evaluation_v1.html

Files allowed to change

  • scripts/run_holdout_live.py — create a single-task opt-in runner.
  • tests/test_holdout_live.py — create offline validation tests using a mocked orchestrator.
  • docs/evaluation_holdout_v1.md — update only if the operator command needs documenting.
  • .awos/holdout_private/ — local ignored artifacts only; never commit private contents.

Atomic implementation steps

Step 1 — Validate one private task manifest.

Load exactly one holdout task and verify repository path, task identity, and SHA-256 metadata before creating a trial.

Exit: invalid, missing, public, or traversal paths are rejected by an offline test.

Step 2 — Enforce the small-run limits.

Reject more than one task, more than one trial, an oversized repository snapshot, or an output root outside the private/temporary roots. Do not install dependencies.

Exit: limit-boundary tests fail closed and a valid tiny repository passes preflight.

Step 3 — Adapt the real orchestrator.

Run EvaluationRunner.run_trial with make_orchestrator_agent(Orchestrator); preserve trajectory, changed paths, acceptance output, cost, latency, retries, and failure reasons.

Exit: an offline mocked orchestrator produces a valid report without provider access.

Step 4 — Require explicit live authorization.

Make live execution opt-in and require provider, model, budget, timeout, network policy, and an explicit confirmation token. Keep default execution provider-free.

Exit: missing authorization causes a non-zero exit before any provider call.

Step 5 — Execute one authorized trial.

Run one task in a fresh temporary workspace with an operator wall-time limit. Stop on safety failure, false success, timeout, or storage pressure.

Exit: one digest-bound candidate report exists, or a preserved failure report explains why it stopped.

Step 6 — Verify and record evidence.

Verify the report bundle with the existing holdout comparison tools and write a new immutable checkpoint containing actual results and limitations.

Exit: comparison exit status and checkpoint agree with evaluator-owned results.

Testing plan

  • Offline adapter tests with a mocked orchestrator.
  • Manifest rejection tests for public paths, traversal, duplicate IDs, and missing hashes.
  • Boundary tests for one task/one trial and repository size.
  • Existing focused evaluation suite: 42 tests currently passing.
  • Live trial remains opt-in and is never required by CI.

Stop conditions

  • Any safety failure or untruthful success report.
  • Unexpected writes outside allowed paths.
  • Timeout, disk pressure, credential ambiguity, or budget ambiguity.
  • Two failed fixes on one problem: switch to explicit debug mode before another code change.
