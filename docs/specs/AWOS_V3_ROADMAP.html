📋 Current Gaps (From Effectiveness Analysis)

❌ GAP 1: No Persistent Memory

Symptom: Agent forgets everything after 15-minute cache TTL. Cross-session learning is zero.

Impact: CRITICAL — Every session starts from scratch. Cannot build institutional knowledge.

Evidence: Session memory dies after 900s TTL. No vector DB. No embeddings.

✅ SOLUTION: Vector Memory System (P0)

What: ChromaDB + sentence-transformers for persistent semantic memory

How:

  • Every interaction stored as (text, embedding, metadata) in ChromaDB
  • Metadata: session_id, timestamp, handler_type, cost, success
  • On new request: semantic search retrieves top-k similar past interactions
  • Injects relevant past solutions into context window
  • Automatic re-indexing when codebase changes (file watcher)

Effort: 4 hours

Cost impact: $0 (local embeddings via all-MiniLM-L6-v2)

Quality impact: Cross-session recall 0% → 80%

❌ GAP 2: Keyword-Based Context Retrieval

Symptom: _read_relevant_context uses naive keyword matching. Misses semantically relevant code.

Impact: HIGH — Context relevance at 60% instead of achievable 90%

Evidence: File scored by keyword overlap in name + first 2000 chars. No understanding of what code actually does.

✅ SOLUTION: Semantic Codebase Index (P0)

What: Embed entire codebase into vector index, query by meaning not keywords

How:

  • On startup: parse all .py files into chunks (function-level, class-level)
  • Embed each chunk with all-MiniLM-L6-v2 (384 dim, local)
  • Store in ChromaDB collection codebase
  • On query: embed query, cosine similarity search, return top-5 chunks
  • Incremental update: when file changes, re-embed only changed chunks

Effort: 6 hours

Cost impact: $0 (local embeddings)

Quality impact: Context relevance 60% → 90%

Dependency: Requires Vector Memory infrastructure (same ChromaDB)

❌ GAP 3: Opaque Reasoning

Symptom: Agent produces outputs but reasoning is invisible. Cannot debug why it chose action X.

Impact: MEDIUM — Can't improve what you can't see. No learning from reasoning patterns.

Evidence: Orchestrator executes steps but doesn't generate intermediate thoughts. No trace of decision-making.

✅ SOLUTION: ReAct Reasoning Traces (P1)

What: Thought → Action → Observation loops, persisted for inspection

How:

  • Before each tool call: LLM generates thought ("I need to find API docs for X")
  • Execute tool → record observation (result)
  • Store trace: {thought, action, args, observation, success, timestamp, latency}
  • Persist to .awos/traces/<session_id>.json
  • CLI: awos traces show <session_id> to inspect
  • Self-correction: if observation shows failure, generate new thought + try alternative

Effort: 3 hours

Cost impact: +$0.0001/req (Gemini Flash for thoughts = negligible)

Quality impact: Debuggable reasoning + self-correction on failures

❌ GAP 4: No Self-Verification Before Return

Symptom: Agent returns outputs without checking correctness. User must catch errors.

Impact: MEDIUM — 15% syntax error rate in sandbox before verifier

Evidence: Worker generates SEARCH/REPLACE but doesn't verify SEARCH exists in file. Verifier catches it downstream.

✅ SOLUTION: Multi-Layer Verification (P1)

What: Three verification layers before returning to user

How:

  • Layer 1 (Worker self-verify): Before returning, verify SEARCH string exists in target file. If not, retry immediately.
  • Layer 2 (Syntax check): Parse generated code with ast.parse. If syntax error, return error + retry.
  • Layer 3 (Spec compliance): LLM-based check: "Does this code satisfy the spec?" (Gemini Flash, $0.0001)
  • If any layer fails: auto-retry with error context injected into prompt

Effort: 2 hours

Cost impact: +$0.0001/req (Gemini Flash for spec check)

Quality impact: Syntax error rate 15% → 5%

❌ GAP 5: No Tool Learning

Symptom: Agent doesn't learn which tools succeed for which tasks. Repeatedly tries wrong tools.

Impact: MEDIUM — Wasted API calls on tools that don't fit the task

Evidence: Every task starts with naive tool selection. No performance tracking.

✅ SOLUTION: Tool Performance Tracker (P2)

What: SQLite DB tracking tool success/failure per task type

How:

  • After every tool call: record {tool, task_type, success, latency, cost}
  • Task type = embeddings of task description (semantic, not keyword)
  • Recommend tools: find similar past tasks (cosine similarity), return tools with highest success rate
  • Decay old data: weight recent outcomes 2× more than old

Effort: 4 hours

Cost impact: $0 (local SQLite, no API calls)

Quality impact: Tool selection accuracy 50% → 85%

❌ GAP 6: Sequential Execution Only

Symptom: All tool calls run sequentially. Independent tasks wait for each other.

Impact: LOW — 30-50% slower than necessary on multi-tool tasks

Evidence: Orchestrator iterates steps in a for loop. No parallelization.

✅ SOLUTION: DAG-Based Parallel Executor (P3)

What: Build dependency graph, execute independent steps in parallel

How:

  • Planner annotates steps with dependencies ("step 2 needs step 1's result")
  • Build DAG: nodes = steps, edges = data dependencies
  • Topological sort → get execution waves
  • Each wave: asyncio.gather() to run all independent steps in parallel
  • Example: [web_search, github_search] → [fetch_url(result)] = 5s vs 7s sequential

Effort: 8 hours

Cost impact: $0 (same number of API calls, just faster)

Quality impact: Speed 30-50% faster. No quality change.

Deferred: Low ROI unless profiling shows significant time wasted

❌ GAP 7: No Failure Recovery Strategy

Symptom: If a tool fails after all escalations, agent gives up. No fallback to simpler approach.

Impact: MEDIUM — Task failure rate stays at 30% for hard tasks

Evidence: EscalationEngine has 5 tiers but no "simplify and retry" strategy.

✅ SOLUTION: Retry with Simplification (P2)

What: When all models fail, try simpler task decomposition

How:

  • If task fails at max escalation: break into smaller sub-tasks
  • Example: "refactor auth system" → ["add auth module", "move functions", "update imports"]
  • Each sub-task gets fresh attempt with lower complexity score
  • Max 2 decomposition cycles to avoid infinite loops

Effort: 2 hours

Cost impact: +$0.001/req (only on failures, most tasks succeed first try)

Quality impact: First-attempt success 70% → 80%

❌ GAP 8: Budget Resets Per Session

Symptom: TokenTracker is in-memory only. Budget counter resets every time agent restarts.

Impact: LOW — Can't track month-to-date spending

Evidence: No persistence for TokenTracker. Budget alerts fire based on session-only totals.

✅ SOLUTION: Persistent Budget Ledger (P1)

What: Save TokenTracker state to .awos/budget.json on every update

How:

  • On record(): append to .awos/budget.json (append-only ledger)
  • On startup: load ledger, compute running totals
  • Monthly reset: detect new month from system date, archive old ledger
  • CLI: awos budget shows month-to-date + projection

Effort: 1 hour

Cost impact: $0

Quality impact: Budget enforcement actually works across sessions

⚠️ Risks & Mitigations

Risk 1: ChromaDB size grows unbounded

Likelihood: Medium | Impact: Medium

Mitigation: Cap collection at 10,000 interactions (~100MB). Evict oldest by timestamp. Prune traces older than 30 days by default.

Risk 2: Embedding quality insufficient for code

Likelihood: Low | Impact: High

Mitigation: Start with all-MiniLM-L6-v2 (free, fast). If code retrieval quality < 80%, upgrade to jina-embeddings-v2-base-code ( specialized for code, still free). Last resort: Gemini embeddings API ($0.0001/1k).

Risk 3: ReAct traces bloat context window

Likelihood: Medium | Impact: Low

Mitigation: Only include last 3 traces in context. Summarize older traces into 1-line descriptions. Truncate observation text to 200 chars.

Risk 4: Tool learning data is sparse initially

Likelihood: High | Impact: Low

Mitigation: Seed with 20 synthetic examples covering common patterns. Fallback to default tool selection if no relevant history. Warm-up period: first 50 tasks use defaults, learning kicks in after.

Risk 5: Parallel execution introduces race conditions

Likelihood: Medium | Impact: Medium

Mitigation: Only parallelize read-only tools (web_search, github_search, hf_search). Write operations (write_file, shell) always sequential. File-level locking for concurrent writes.
