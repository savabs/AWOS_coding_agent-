1. Problem Statement

AWOS's edit pipeline is fragile because it parses free-form text blocks from LLM responses. The three root failure modes, each causing distinct failure signatures in eval:

Failure ModeRoot CauseSymptom in EvalFrequency
SEARCH block not foundLLM reconstructs from snippet, not exact fileverifier fails, task score 0~40% of L3 failures
Wrong location appliedMultiple matches, first match selected silentlyWrong code modified, test fails~20% of L3 failures
Parse failureLLM emits malformed block delimitersNo edit applied, silent pass or score 0~15% of failures
Context driftSnippet extraction misses surrounding codeold_string references code not in snippet~25% of L3 failures
The fundamental problem: The LLM writes SEARCH blocks based on a snippet of the file, not the full content. Claude Code enforces: you MUST read the full file before editing. AWOS currently passes a compressed context_snippet. This is the root cause of L3 multi-file failures.

2. P0.1 — JSON Structured Edit Format

2.1 Motivation

Claude Code, Cursor, and all major production coding agents use structured JSON tool calls for edits — not text block parsing. The LLM emits machine-readable JSON; the tool validates and applies it. This eliminates an entire class of parsing errors.

❌ Current AWOS approach

LLM emits freeform text:

<<<<<<< SEARCH def old_method(self): pass ======= def old_method(self): return True >>>>>>> REPLACE

AWOS then regex-parses this text. Fails if LLM omits spaces, changes quote style, gets delimiters slightly wrong.

✅ New approach (like Claude Code)

LLM emits structured JSON:

{ "edits": [ { "old_string": "def old_method(self):\n pass", "new_string": "def old_method(self):\n return True" } ] }

Worker validates JSON schema, checks old_string exists, applies. Zero regex parsing.

2.2 New Prompt Format for LLM

The worker prompt will instruct the LLM to respond in this exact JSON schema:

## OUTPUT FORMAT Respond ONLY with valid JSON. No markdown, no explanation, just JSON: { "reasoning": "One sentence explaining the change", "edits": [ { "old_string": "exact text from the file to replace (can be multiple lines)", "new_string": "replacement text" } ] } RULES: - old_string MUST be an exact substring of the file content shown above - Include enough surrounding context (2-3 lines) to be unique in the file - If adding new code with no replacement, use the line just before the insertion as old_string, and include it in new_string too - For a new file (empty), set old_string to "" and new_string to the full content - Multiple edits are applied in order — earlier edits affect later ones

2.3 Worker Changes — execute_task() Flow

Step 1 Full file read: Before calling LLM, always read the full file content (not snippet). Store it as full_content.
Step 2 Context extraction: Extract relevant portion (unchanged) — but also pass full_content to the verifier.
Step 3 LLM call with JSON schema: Prompt includes file content + JSON output instructions.
Step 4 JSON parse response: json.loads(response) — no regex. If fails → structured error + retry.
Step 5 Pass EditRequest to verifier: EditRequest(file_path, full_content, edits=[...])
Step 6 Verifier applies & validates: Verifier checks each edit, applies sequentially, returns modified content.
Step 7 Write to disk: Only after all edits validated successfully.

2.4 Detailed Code Spec — _parse_llm_response()

def _parse_llm_response(self, response_text: str) -> list[dict]: """ Parse JSON edit response from LLM. Returns list of {old_string, new_string} dicts. Raises ValueError with actionable message on failure. """ # Strip markdown if present (defensive) text = response_text.strip() if text.startswith("```"): # Extract content between first ``` and last ``` lines = text.split("\n") start = 1 if lines[0].startswith("```") else 0 end = len(lines) - 1 if lines[-1].strip() == "```" else len(lines) text = "\n".join(lines[start:end]) try: data = json.loads(text) except json.JSONDecodeError as e: raise ValueError(f"LLM response is not valid JSON: {e}\nResponse was:\n{text[:500]}") if "edits" not in data: raise ValueError(f"JSON response missing 'edits' key. Got keys: {list(data.keys())}") edits = data["edits"] if not isinstance(edits, list) or len(edits) == 0: raise ValueError(f"'edits' must be a non-empty list, got: {type(edits)}") for i, edit in enumerate(edits): if "old_string" not in edit or "new_string" not in edit: raise ValueError(f"Edit {i} missing 'old_string' or 'new_string': {edit}") return edits

2.5 Backward Compatibility

Strategy: Keep the existing _parse_search_replace() as a fallback for models that still emit SEARCH/REPLACE blocks. Try JSON parse first; if it fails, try legacy SEARCH/REPLACE parse; if both fail, return structured error to LLM.
def _parse_response(self, response_text: str) -> list[dict]: """Try JSON first, fall back to SEARCH/REPLACE.""" # 1. Try JSON try: return self._parse_json_edits(response_text) except ValueError: pass # 2. Try legacy SEARCH/REPLACE blocks try: return self._parse_search_replace(response_text) except ValueError: pass # 3. Both failed — return empty (will trigger error + retry) return []

3. P0.2 — Read-Before-Write Enforcement

3.1 Problem

Currently, _extract_context() returns a snippet (200-300 lines) of the file, not the full content. The LLM writes edits based on this snippet. When the LLM's old_string references code outside the snippet (or code that differs even slightly from the snippet), the edit fails.

In the L3 task "Add snapshot() to ToolPerformanceTracker + wire to Orchestrator", the orchestrator.py file is ~900 lines. The snippet extraction was finding a ~200 line window. The constructor where self.performance is initialized (line ~80) and the execution summary (line ~750) are both critical but likely outside the snippet. The LLM is writing edit blocks it can't reliably anchor.

3.2 Solution: Full File Read + Smart Context Injection

New approach in execute_task():

def execute_task(self, task, file_content, ...): # FULL content always read first full_file_content = file_content # caller already provides this # Smart context: extract the MOST RELEVANT section for display # but always anchor edits against full_file_content display_context = self._extract_context(full_file_content, task["action"]) # Build prompt with display_context for readability # but edits are validated against full_file_content prompt = self._build_prompt( task=task, display_context=display_context, full_content_line_count=len(full_file_content.split('\n')), ... ) # ... LLM call ... # ALWAYS validate against FULL content return self._apply_and_verify( full_content=full_file_content, edits=parsed_edits, task=task, )

3.3 Prompt Change — Include File Header + Tail

The prompt template must clearly show the LLM where the context comes from in the full file:

## FILE: {task['file']} ({total_lines} lines total) ### File Header (lines 1-{header_end}): {header_content} ### Relevant Section (lines {start}-{end}): {relevant_context} ### File Tail (lines {tail_start}-{total_lines}): {tail_content} NOTE: Your old_string MUST be an exact substring of this file's content. The full file has {total_lines} lines. Only part is shown above.

3.4 When File is Small (< 300 lines)

If the target file is under 300 lines: include the ENTIRE file in the prompt. No extraction needed. This is the highest-reliability path.

MAX_FULL_FILE_LINES = 300 # Below this, show entire file def _get_file_context(self, full_content: str, action: str) -> str: lines = full_content.split('\n') if len(lines) <= MAX_FULL_FILE_LINES: return full_content # Show everything else: return self._extract_smart_context(full_content, action)

4. P0.3 — Multiple-Match Detection

4.1 Problem

If old_string appears multiple times in a file (e.g., a common pattern like return None or self.x = None), the current code applies the edit to the first match silently. This can corrupt the wrong part of the file.

4.2 Solution: Count Before Apply

def _apply_single_edit( self, content: str, old_string: str, new_string: str, replace_all: bool = False, edit_index: int = 0, ) -> tuple[str, str | None]: """ Returns (new_content, error_message). error_message is None on success. """ if old_string == "": # File creation — valid only if content is also empty if content.strip() != "": return content, "Cannot use empty old_string on non-empty file" return new_string, None count = content.count(old_string) if count == 0: # Find nearest match for helpful error nearest = self._find_nearest_match(content, old_string) return content, ( f"Edit {edit_index}: old_string not found in file.\n" f"Nearest match found:\n---\n{nearest}\n---\n" f"Ensure old_string exactly matches file content including whitespace." ) if count > 1 and not replace_all: # Show all match locations for debugging locations = self._find_all_match_lines(content, old_string) return content, ( f"Edit {edit_index}: old_string found {count} times in file " f"(lines: {locations}). " f"Add more surrounding context to make it unique, " f"or set replace_all=true to replace all occurrences." ) if replace_all: return content.replace(old_string, new_string), None else: return content.replace(old_string, new_string, 1), None

4.3 Find Nearest Match Helper

def _find_nearest_match(self, content: str, old_string: str) -> str: """Find closest matching line using difflib for helpful error messages.""" import difflib target_lines = old_string.strip().split('\n') content_lines = content.split('\n') # Find the line in content most similar to first line of old_string first_target = target_lines[0].strip() best_ratio = 0.0 best_idx = 0 for i, line in enumerate(content_lines): ratio = difflib.SequenceMatcher(None, first_target, line.strip()).ratio() if ratio > best_ratio: best_ratio = ratio best_idx = i # Show window around best match start = max(0, best_idx - 2) end = min(len(content_lines), best_idx + len(target_lines) + 2) return '\n'.join(content_lines[start:end])
