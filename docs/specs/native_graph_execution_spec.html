Spec: Native Graph Execution

Status: active · Phase: 1 · Date:

2026-08-03

Goal

When the advanced Planner returns a validated execution_graph, the orchestrator executes that graph directly while preserving legacy task-list and CheapPlanner fallback behavior.

Simple meaning: the Planner draws the route; the orchestrator follows the route; cheap workers perform

only the small jobs assigned to them.

Governing research: native_graph_execution.html

Implementation Stepsh2>

Step 1 — Select native graph output

At the planning boundary, choose execution_graph only when it is present and passes the existing native contract validator. Otherwise retain the existing legacy plan path.

Verification: provider-free tests prove native responses select the graph and legacy/CheapPlanner responses select compatibility execution.>

Step 2 — Restore the graph at the runtime boundary

Convert normalized Planner graph data into >ExecutionGraph objects and validate persisted session graphs before resume. Invalid graphs return a controlled planning/execution failure.

Verification: malformed, cyclic, unknown-dependency, and corrupt-session graph tests fail closed.

Step 3 — Dispatch edit nodes through the existing worker

Map one native edit node to the existing atomic task dictionary and execute it through _execute_single_task().

Verification: a mocked edit node reaches the worker once with the correct node ID, files, action, acceptance check, and retry metadata.p>

3>Step 4 — Dispatch read-only and verification nodes

Implement explicit callbacks for explore, test, barrier, review, and final verification nodes without routing them through the edit worker.

>Verification: tests assert each node type uses the correct provider-free callback and that a failed test blocks ordinary descendants.

Step 5 — Persist each native execution wave

Save the graph before execution, after every completed wave, and after the final graph state through the existing RuntimeSession store.

Verification: a pause/resume test reloads statuses and does not rerun completed nodes.

Step 6 — Update GoalGraph progress

Map stable native node IDs into Goal

Graph progress updates and keep aggregate task counts consistent with graph nodes.

Verification: completed and failed native nodes produce the expected GoalGraph state and execution summary.

Step 7 — Preserve legacy behavior

>Run the existing legacy task-list and CheapPlanner paths without

native graph assumptions.

Verification: existing ProjectPlanner, orchestrator integration, and minimal

E2E tests remain green.

<h3>Step 8 — Run the focused regression gate>

Run native graph, execution graph, runtime

session, ProjectPlanner, orchestrator integration, and minimal E2E tests.

Verification:> record the exact passing count and separately report known repository-wide lint/full-suite limitations.

Step 9 — Run the multi-module evaluation

Execute a provider-free 10–20-file graph fixture containing independent branches, cross-module dependencies, test barriers, one intentional failure, recovery, pause/resume

, parallel waves, and cost/latency telemetry.

Verification: the evaluation report proves ordering, concurrency, recovery, persistence, and bounded accounting.

Edge Cases

  • Native graph missing: use legacy plan.
  • Legacy plan missing or malformed: fail closed before edits.
  • Unknown dependency or cycle: fail closed; never force a node forward.
  • Failed test/barrier: ordinary descendants remain blocked
    • .
  • Recovery node: runs only
    • through explicit graph recovery semantics.
  • Same-file
    • writes: remain serialized by graph conflict rules.
  • Resume after a completed
    • wave: completed nodes are not executed again.li>
  • CheapPlanner fallback: remains task-level
    • and is never treated as the project decomposition authority.
