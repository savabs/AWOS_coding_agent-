Spec: Execution Graph Integration

<strong>Status: ready for implementation · Phase: 1 · <strong>Research: execution_graph_integration.html

Goal: make the typed ExecutionGraph the validated runtime plan for orchestrated execution while preserving the advanced Planner, GoalGraph, cheap workers, and backward-compatible sessions.

Exit Conditions

    <li>Accepted Planner task dictionaries compile deterministically into a validated ExecutionGraph.
  • Typed graph execution
    • produces safe waves and updates node status from executor results.
  • Graph state survives RuntimeSession JSON round-trip and resume.
    • >Failed nodes block ordinary descendants and expose explicit recovery insertion.
  • Provider-free integration tests
    • pass; legacy non-graph behavior remains covered.

Files Authorized>
  • scaffold/agent/execution_graph.py — add deterministic plan-task compilation helpers only.
  • scaffold/agent/dag_executor.py — add a graph-aware adapter or execution method; do not weaken existing task behavior.
  • scaffold/agent/runtime_session.py — persist an optional execution-graph payload backward-compatibly.
  • scaffold/agent/orchestrator.py> — compile, restore, execute, and persist graph state through the narrow batch seam.
  • tests/test_execution_graph_integration.py — provider-free integration tests.
  • tests/test_runtime_session.py — only if the existing session contract requires a focused compatibility assertion.

Explicitly not authorized: Planner prompt/model changes, ProjectPlanner schema replacement, UI changes, new dependencies/providers, or broad orchestrator refactors.

Atomic Implementation Steps

Step 1 — Compile legacy plan tasks.

Add one deterministic compiler that maps current task dictionaries to typed nodes, preserves task IDs in metadata, carries explicit depends_on, acceptance, evidence, and file fields, and adds conservative same-file ordering.

Proof: compiler tests cover mapping, stable IDs, file ordering, and malformed input rejection.

Step 2 — Add graph-aware execution adapter.

Add a narrow DAGExecutor method that accepts an ExecutionGraph and callback, runs only ready waves, records completed/failed status, and never force-releases cycles.

Proof: an integration test proves parallel independent nodes, ordered same-file nodes, and failed-prerequisite blocking.

Step 3 — Persist graph state in RuntimeSession.

Add an optional serialized graph field with old-session defaults and round-trip behavior.

Proof: old payload and new payload compatibility tests pass.

Step 4 — Route orchestrator parallel batches through the graph.

At the existing batch seam, compile or restore the graph

, invoke the graph-aware adapter, and translate node results to the existing result shape without changing sequential execution.

Proof: provider-free orchestrator integration test verifies the callback receives atomic task metadata and statuses persist.

Step 5 — Persist evidence and recovery state.

When a callback returns success/f

ailure and optional evidence, update the graph node and RuntimeSession before the next wave; preserve failed nodes as failed and allow only explicit recovery nodes past them.

Proof: failed test → recovery → retry test proves ordering and resume state.

Step 6 — Run focused regression validation.>

Run the new integration suite plus the existing execution

-graph, ProjectPlanner, DAGExecutor, and RuntimeSession focused suites.

Proof: report exact pass/fail counts; do not claim full-repository green while known unrelated failures remain.

Compatibility Rules>
  • Existing task
    • dictionaries remain accepted at the public orchestrator boundary.
  • Existing RuntimeSession JSON without a graph
    • loads as an empty/absent graph.
  • GoalGraph progress remains updated
    • through existing ProjectPlanner calls.
  • Sequential mode remains unchanged in this
    • slice.
  • Cycle errors fail closed; no forced scheduling.>
