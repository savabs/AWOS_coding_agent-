Spec: Evidence-First Debugger

doc/spec phase/1 topic/evidence-first-debugger active 2026-07-26

Goal

Create an AWOS debugging subsystem that records agent runs as structured evidence, distinguishes PROVEN issues from HYPOTHESIS and UNKNOWN, and supports proof-by-rerun so the coding agent stops hallucinating unsupported bug claims.

Governing research: evidence_first_debugger.html
Task file: evidence_first_debugger_task.html

Normative Truth Contract — Frozen Planning Version

This contract is the authority for all debugger implementations and reports. A finding is always a claim about a defined subject; status must never describe a vague session-level impression.

Claim scope

Claim typeExampleWhat may be proven
OBSERVATIONA test command exited nonzero and emitted a traceback.The recorded command outcome and captured output, if the artifact is valid.
DIAGNOSISThe parser rejected a specific file at a specific location.The tool-reported diagnostic, including its source location.
ROOT_CAUSEA specific edit caused the test failure.Only when a rule or controlled rerun establishes the required causal relationship.
REMEDIATIONA proposed patch will fix the failure.Only after validation demonstrates the expected outcome; a plan alone is a hypothesis.

Status semantics

  • PROVEN: the exact claim has at least one valid proof record. The record names the rule, evidence IDs, source artifact references, and environment/run identity. A proven observation does not promote related causal claims.
  • HYPOTHESIS: the claim is supported by non-proof signals or an incomplete proof attempt and is worth investigating. It must be presented as a candidate, never as an established issue.
  • UNKNOWN: available evidence is absent, invalid, contradictory, out of scope, or too weak to justify even a ranked hypothesis.

Evidence classes

ClassMeaningCan prove a claim alone?
DIRECT_OBSERVATIONRaw output or event from a real tool, process, verifier, parser, test runner, or edit operation.Only when a matching deterministic rule accepts it and the claim scope matches.
DERIVED_PROOFAuditable result produced by a versioned deterministic proof rule from direct observations.Yes, for the exact rule-scoped claim.
RERUN_REPRODUCTIONA later controlled run that reproduces a prior claim under recorded equivalence conditions.Yes for reproducibility; causal claims require the stronger causal rule.
ATTRIBUTION_SIGNALFault localization, similarity, recency, repeated failure, model judgment, or ranking score.No.
EVIDENCE_GAPMissing, corrupt, truncated, redacted, conflicting, or unavailable evidence.No; it constrains the result toward UNKNOWN.

Proof and transition rules

  1. A proof rule must declare its ID and version, accepted evidence classes, claim type, required fields, and scope of conclusion.
  2. PROVEN is permitted only when all required evidence references resolve to valid, integrity-checkable artifacts and the rule passes.
  3. A nonzero exit proves a process failure, not its root cause. A failing test proves a test failure, not automatically the faulty line.
  4. Heuristic or LLM-only evidence may create or rank HYPOTHESIS findings, never PROVEN findings.
  5. Failed, divergent, or inconclusive reruns append validation evidence. They do not delete or silently rewrite the original finding.
  6. Evidence conflicts produce separate linked claims or an explicit conflict record; the engine must not hide disagreement by merging it.
  7. Finding history is append-only. Any later interpretation must reference the prior finding and the new evidence.

Required proof record

Every PROVEN finding must carry: finding_id, claim type and subject, status, proof_rule_id, proof-rule version, evidence IDs, source paths plus offsets or event IDs, artifact hashes when available, run/environment identity, observed timestamp, and a human-readable bounded conclusion.

Implementation Steps

Each step is atomic: changes one thing, tests one thing, proves one thing.

Step 1
Create the canonical debugger truth model

Create scaffold/agent/core/debug_schema.py with the core enums and dataclasses for FindingStatus (PROVEN, HYPOTHESIS, UNKNOWN), EvidenceKind, FailureStage, DebugEvidence, and DebugFinding. Truth status must be explicit and serializable.

Exit condition: A unit test proves schema round-trips through JSON without collapsing PROVEN, HYPOTHESIS, and UNKNOWN into the same representation.
Step 2
Create the canonical debug report model

Create scaffold/agent/core/debug_report.py with task-level and session-level report objects that group findings, artifact references, normalized cause chains, and rerun outcomes.

Exit condition: A unit test creates a session report with multiple task findings and confirms deterministic serialization/deserialization.
Step 3
Create an append-only debugger journal and bundle layout

Create scaffold/agent/core/debug_journal.py and a canonical disk layout under .awos/debug/<session_id>/ for findings, evidence references, manifest data, and rerun outcomes.

Exit condition: A test run writes a valid debug bundle with a manifest and at least one append-only findings/evidence artifact file.
Step 4
Adapt TaskSpan records into debugger evidence

Add an adapter that converts TaskSpan data from scaffold/agent/core/observability.py into normalized DebugEvidence records for latency, model routing, cost, and attempt facts.

Exit condition: A fixture TaskSpan produces evidence records with stable IDs and preserved routing/timing fields.
Step 5
Adapt GuiEventBus events into debugger evidence

Add an adapter for .awos/gui/<session>/events.jsonl so the debugger can consume ordered runtime events such as session start, plan generation, model routing, task start, file edit, test result, task complete, session done, and synthetic crash error events.

Exit condition: A sample events.jsonl file normalizes into ordered evidence items with event type, timestamp, payload, and source reference.
Step 6
Normalize legacy and current event vocabularies into one canonical taxonomy

Introduce a compatibility layer that maps legacy names like planning_done, worker_start, worker_done, verify_result, task_done, retry_notice, and file_change into the same canonical schema used by GuiEventBus and the debugger core.

Exit condition: A compatibility test proves that old and new session artifacts normalize to identical canonical event/evidence structures.
Step 7
Create deterministic proof rules for runtime failures

Create scaffold/agent/core/debug_rules.py with deterministic rules for nonzero subprocess exit, verifier rejection, failing test with traceback, syntax/parser/import failure, and failed edit application. These are the first allowed paths to PROVEN.

Exit condition: Tests prove that each supported failure class yields PROVEN only when the corresponding recorded artifact exists.
Step 8
Adapt verification and test artifacts into proof evidence

Wire verifier/test/build outputs from existing runtime components and TaskTelemetry into the deterministic rule engine so verification failures and test failures produce explainable evidence bundles.

Exit condition: An integration test proves that a failing verification or failing test produces a PROVEN finding with artifact references to the concrete output that triggered it.
Step 9
Integrate FaultLocalizer as attribution input only

Feed FaultLocalizer.localize() results into debugger attribution as ranked candidate causes, but explicitly prevent localization confidence from creating PROVEN findings by itself.

Exit condition: A test proves that localization-only evidence can produce ranked HYPOTHESIS findings but never upgrades them to PROVEN.
Step 10
Create a ranked suspicion engine for non-proof signals

Implement investigation ordering over stack traces, verifier/test alignment, localization rank, recent edits, repeated failures, and stage consistency. This engine is for prioritization only.

Exit condition: A deterministic fixture produces a stable ranking order across repeated runs, while all findings remain HYPOTHESIS or UNKNOWN without proof artifacts.
Step 11
Create a rerun/checkpoint request model

Define the debugger’s proof-by-rerun request format: which session/task/event boundary is being resumed from, which inputs are frozen, which runtime capabilities are required, and where new evidence should be attached.

Exit condition: A unit test proves that the rerun request format can represent session-, task-, or event-scoped repro attempts without ambiguity.
Step 12
Implement proof-by-rerun status resolution

Add logic that updates findings after reproduction attempts: reproduced failures can upgrade or confirm a finding, non-reproduced failures remain non-proven, and divergent reruns are recorded as separate evidence rather than silently overwriting the prior record.

Exit condition: Integration tests prove that rerun outcomes update finding status according to explicit rules and never silently convert missing proof into proof.
Step 13
Add debugger CLI/API inspection surfaces

Add a low-friction way to inspect reports and rerun plans, either via awos.py commands, server endpoints, or both. The first phase should prioritize machine-readable output for the coding agent over polished UX.

Exit condition: A debug report for a saved session can be retrieved and inspected without opening the web UI.
Step 14
Add debugger UI surfaces to the Agent Console

Extend the app so users can see debugger findings, evidence references, proof status, failure stage, and rerun result directly in the main interface. The UI should clearly separate facts from hypotheses.

Exit condition: A clean success run and a failing run both render debugger status in the UI, and the failure run visibly distinguishes PROVEN from HYPOTHESIS.
Step 15
Create a debugger benchmark and anti-hallucination regression suite

Add fixtures and tests that cover process crashes, verifier rejection, failing tests, syntax errors, localization-only suspicion, missing-artifact cases, and rerun divergence. The suite must explicitly guard the no-hallucinated-proof contract.

Exit condition: A regression test proves that unsupported cases remain HYPOTHESIS or UNKNOWN instead of incorrectly becoming PROVEN.
Step 16
Add optional OpenTelemetry/OpenInference export

Once native AWOS reports are stable, add optional export or dual-write so external observability systems can ingest the traces. AWOS’s local debug report remains the source of truth; the export is a transport/viewer integration.

Exit condition: A test proves that one session can be exported with correlated OpenTelemetry/OpenInference metadata while the native AWOS debug bundle remains authoritative.

Edge Cases

  • No verifier/test/build artifact exists — the debugger must emit UNKNOWN or a low-priority HYPOTHESIS, not a proven failure.
  • Multiple proof artifacts disagree — the debugger must preserve both findings or preserve precedence rules explicitly, not silently merge them.
  • Telemetry files are truncated or partially corrupt — ingestion should record an evidence gap rather than invent a failure.
  • A subprocess crashes before session_done — the synthetic crash event from gui/server.py must remain attached as explicit evidence.
  • Legacy event names appear in historical sessions — normalization must preserve meaning without breaking modern sessions.
  • Rerun diverges because of nondeterminism, provider variance, or changed workspace state — the original finding must not be overwritten.
  • Prompt/tool content is sensitive — export and UI paths need redaction controls without destroying structural evidence.
