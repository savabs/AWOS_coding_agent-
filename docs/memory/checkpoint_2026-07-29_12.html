<h2>1. Executive summary

This session moved AWOS from a small collection of coding-agent tests toward an evidence-first evaluation system. The project now has two distinct proofs:

  1. A focused offline proof that the core coding-agent loop can explore/plan/edit/test/retry/rollback and report outcomes correctly.
  2. A deterministic evaluation harness that can run isolated task fixtures, apply evaluator-owned acceptance tests, detect unsafe writes, preserve trajectories, aggregate multiple trials, replay reports, and compare a candidate against a baseline.

The real orchestrator is now connected to the evaluation harness through an adapter. The adapter records the orchestrator’s result as evidence, but it does not trust the orchestrator’s self-reported success as the final correctness decision. That separation is essential: an agent can report success while hidden or evaluator-owned tests still fail.

Current honest status: AWOS has a working offline coding-agent core and a working deterministic evaluation framework. It is not yet proven to be production-equivalent to Cursor or Hermes across a broad held-out corpus, and the repository-wide test suite is not green.

2. Product direction and objective

AWOS is not being built as a generic Cursor clone. The project identity remains a learnable operating system whose first application is

a proper coding agent. Cursor, Hermes, OpenHands, SWE-agent, and related systems are capability benchmarks, not implementation templates.

The desired objective is:

Quality × Speed ÷ Cost

Quality is a hard floor. Speed and cost are tunable only after correctness and safety pass. A cheap, fast, incorrect patch is not an improvement. A reward signal must never make a failed coding task look successful.

4. Evaluation architecture now in placeh2>

4.1 Fixture schema

Each evaluation fixture includes:

  • Stable task ID and task family.
  • Repository snapshot/path.
  • Public user request.
  • At least one required executable acceptance command.
  • Structured argv commands instead of shell strings.
  • Allowed paths and forbidden paths.
  • Optional human-calibrated task duration.
  • Schema version evaluation_v1.

A fixture without an acceptance oracle is rejected. Absolute paths and parent traversal paths are rejected. This prevents an evaluation from silently becoming a subjective “looks good” test.

<

h3>4.2 Trial execution

For every trial, the runner:

  1. Resolves and validates the source repository.
  2. Copies it into a fresh temporary workspace.
  3. Snapshots
    4. file contents and symlinks before the agent runs.
  4. Invokes an agent callback.
  5. Snapshots the workspace after execution
    6. .
  6. Computes changed paths.
  7. Checks all changes against allowed and forbidden paths.
  8. Runs evaluator-owned acceptance commands with
    9. >shell=False and a timeout.
  9. Records trajectory events and a terminal trial result.
  10. C
    11. leans the temporary workspace unless explicitly configured otherwise.

The source fixture is never modified by the evaluation run.

<h3>4.3 Hard outcome contract
success = acceptance_passed AND safety_passed AND truthful_report

A test failure, timeout, error, forbidden write, unallowed write, malformed result, or false success is a failed evaluation. A high reward cannot compensate for a failed hard gate.

4.4 Trajectory contract3>

Trials preserve ordered events such as:

<pre>trial_started → orchestrator_started → orchestrator_task → workspace_checked →

acceptance_finished → trial_finished

The saved trajectory contains enough information to inspect what happened without invoking a model again. The current replay command validates and prints the report; deeper state reconstruction remains future work.

4.5 Multi-trial metrics

Reports currently include:

  • pass_at_1 — fraction of successful trials.
  • all_trials_passed — whether

    every trial succeeded.
  • safety_failure_rate.
  • Mean latency.
  • Mean cost.
  • Mean retries.
  • Per-trial failure
    • reasons and trajectories.li>

The current implementation uses the term pass_at_1 as the observed fraction across executed trials. A future report schema should distinguish conventional pass@1 sampling semantics from repeated-trial success probability if those become statistically different.

4.6 Regression comparison

Baseline/candidate comparison reports correctness and safety regressions independently. A candidate with lower pass rate or higher safety failure rate is marked regressed even if it is faster or cheaper.

5. Real orchestrator adapter

The adapter is make_orchestrator_agent() in <

code>scaffold/agent/evaluation_v1.py. It calls the existing boundary:

Orchestrator.execute_feature(
    goal=fixture.request,
    codebase_root=isolated_workspace,
    pre_planned_tasks=optional_tasks,
)

It converts the returned execution log and summary into trajectory events and passes cost/retry information to the evaluator. It does not make the orchestrator’s success field authoritative.

The CLI exposes this only through:

python3 scripts/run_evaluation_v1.py --mode live --fixture <fixture.json>
Live mode was not run in this session. No explicit provider credentialed execution was requested or available for this proof. Running live mode may make API calls, consume budget, and produce nondeterministic results. The default CLI remains provider-free.
6. Research performed and lessons learned
6.1 SWE-bench
The official SWE-bench documentation confirms a useful structure: apply generated patches to repository environments, run tests in reproducible/containerized environments, and grade resolution from test outcomes. AWOS already has a SWE-bench Lite script, but it is an external realism benchmark rather than the fast default regression gate.
6.2 OpenHands and benchmark breadth
OpenHands evaluation material emphasizes configurable bounded runs, reusable benchmark integrations, and broad task families. The important lesson is that issue resolution alone is insufficient. AWOS must also test greenfield work, information gathering, testing, safety, and long-horizon behavior
.
6.3 METR
METR’s task-completion time-horizon work shows why a single average success score
 is inadequate. Tasks should be diverse and calibrated by human duration; reliability should be examined as task difficulty increases. AWOS should eventually report success curves by human-minutes and task family.
6.4 HELM and evaluation best practices
HELM reinforces standardized datasets, reproducible runs, multiple metrics, and transparent inspection.
 Evaluation best-practice guidance reinforces task-specific graders, complete logging, automation, human calibration, and avoiding “vibe-based” judgments.
6.5 Main project lesson
Self-learning before reliable evaluation
 is dangerous. If the reward signal is wrong, the agent can learn to optimize the evaluator instead of solving coding tasks. The evaluator must be built before trusting reward or self-improvement claims.

<h2>8. Failures and how they were handled
Repository-wide suite remains red.
The latest broad maintained run was 1195 passed, 28 failed, 23 deselected. Failures remain in legacy CLI/session behavior, routing/provider assumptions, create-task functionality, online integration, mission fixtures, self-learning legacy expectations, and environment/order-sensitive E2E. These were not hidden or weakened.
8.1 Test-out
come timeout
A deliberately failed test entered automatic verifier replan and decomposition, causing a timeout. Root cause: the result was classified as verify_fail even when executed tests had failed. The fix introduced terminal test_fail classification and stopped replanning/decomposition for test evidence failures. The regression now passes and explicitly rejects replan/decomposition on test failure.
8.2 Harness collection crash
test_budget_hard_stop.py previously executed at import time and called sys.exit. It was converted into a real pytest assertion with CLI behavior under a main guard. Connectivity tests were marked integration-only. Pytest collection was constrained to the maintained tests/ tree and excluded historical fixture snapshots.>
8.3 Core E2E environment sensitivity
The legacy outcome-gate tests require AWOS_REACT_WORKER=0, while the ReAct/orchestrator E2E requires AWOS_REACT_WORKER=1. Running broad tests together can cause order/environment failures. The correct practice is to run separate explicit gates until test isolation is repaired.
8.4 Adapter test failure
The first adapter test failed because the test fake used Path without importing it. The evaluator correctly recorded an agent_error and acceptance failure. The test was corrected; the adapter suite then passed 12 and subsequently 13 tests.
8.5 Static diagnostics
The language server reports extensive pre-existing typing/import/style diagnostics in legacy modules, especially orchestrator.py. Runtime tests are currently the primary proof. New evaluator code also receives typing warnings because this repository uses older broad typing styles; this is technical debt, not a claimed clean static-analysis gate.
9. Known limitations that must not be forgotten
  • The sandbox is currently worktree/process-level, not full container isolation.
  • Network isolation and secret isolation are not fully enforced by the current sandbox.
  • The evaluator detects changed files inside the copied workspace, but it is not yet a complete OS-level escape detector for arbitrary child processes.
  • Acceptance output is truncated after subprocess completion in some existing components; streaming memory-bounded output remains future work.
  • The live adapter has not yet been executed with real provider credentials in this checkpoint.
  • Public fixtures are small
    •  and deterministic; they do not establish Cursor/Hermes-level capability.
  • No private holdout corpus exists yet.
  • Reward is currently a simple hard-gated diagnostic value in the new runner; it is not yet
    •  connected to a validated self-learning update loop.
  • Replay currently validates and displays reports; it does
    •  not yet recreate every filesystem state transition.
  • Cost values from the orchestrator adapter depend on the orchestrator result and may be zero when callers do
    •  not populate total cost.
  • Full repository health is not established.

Priority 1 — Credentialed live proof
<strong>Run the real orchestrator adapter on a public fixture with an explicitly configured provider.

Add stronger report semantics and tests.
Distinguish pass@1 from repeated-trial reliability, capture acceptance output summaries, preserve environment hashes, and test timeout/collection-error behavior explicitly.
Priority 3 — Build the held-out corpus
Create private evaluation fixtures outside the public fixture directory.
Cover basic edits, exploration, multi-file changes, debugging, test generation, configuration, security, ambiguous requirements, and long-horizon tasks. Do not use holdout tasks for prompt or reward tuning.
Priority 4 — Baseline/candidate CI gate
Make candidate reports fail CI on correctness or safety regressions.
Run public deterministic fixtures on every relevant change. Compare held-out reports only in controlled evaluation runs.
Priority 5 — Real trajectory integration
Persist full orchestrator/debug evidence into evaluator reports.
Link debug bundles, execution logs, diffs, test results, tool calls, model calls, tokens, cost, and rollback evidence by stable session/trial IDs.div>
Priority 6 — Containerized external evaluation
Strengthen isolation before serious external benchmarks.<br>Use container/worktree isolation, explicit network policy, secret filtering, bounded processes, cleanup, and reproducible environment manifests. Then run the SWE-bench Lite subset.

Triage the 28 remaining failures atomically.
Split into CLI/session, routing, create-task, online integration, reviewer signatures, mission fixtures, self-learning expectations, and test isolation. Do not weaken tests or add live APIs to offline gates.
