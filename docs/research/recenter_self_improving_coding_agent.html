Research: Recenter Self-Improving Coding Agent

doc/research phase/4 topic/self-improving-coding-agent active 2026-07-26

Current Architecture

AWOS currently has a split identity across the repository. The user clarified the intended architecture and build order: (1) build a proper coding agent, (2) make it self-learning by helping it solve its own prior failures, (3) use that agent core to expand into an AI-operated OS. This means CI Rescue, agency GTM, customer-lock-in, and generic compounding-on-repo framing are not the project identity.

Research conclusion: the repo needs a second consistency pass that makes the philosophy explicit: coding agent first, failure-driven self-learning second, OS expansion third. The app is the interface to talk to the agent. The system is allowed to use LLMs, ML, DL, RL, databases, memory, tooling, systems engineering, and low-level optimization — anything that raises Quality × Speed ÷ Cost.

Data Flow

  1. Canonical identity originates in VISION.md and is repeated or summarized in README.md, AWOS.md, AGENT_INDEX.md, and memories/repo/project_structure.md.
  2. Planning and product docs echo that identity into task files, product pages, UI copy, and launch positioning.
  3. User-visible interfaces such as the dashboard and Electron shell reinforce whichever framing those docs encode.
  4. Historical checkpoints and .awos/ runtime state record past reality and should not be rewritten as if history never happened.

Observations

Key Findings

  • Canonical drift: the repo now has a second layer of drift: some files still assume self-learning means customer/repo compounding, pricing leverage, or GTM. The user clarified that self-learning means the agent gets better at solving its own failures.
  • Pathway correction: source of truth is now: proper coding agent first; self-learning coding agent second; AI-operated OS third.
  • Technology scope: the harness is not limited to LLM prompting. ML, DL, RL, memory systems, databases, tooling, systems engineering, GPU/CUDA work, and low-level optimization are all in scope if they improve Quality × Speed ÷ Cost.
  • Mutable vs immutable: active docs, canonical docs, product docs, README, UI copy, prompts, and guidance files are fair update targets; checkpoint files are explicitly immutable historical records.
  • Generated/runtime state: files under .awos/ look like chat history, goal history, event logs, benchmark state, and learned telemetry. Rewriting them would falsify runtime history and should be avoided unless there is an explicit migration requirement.

Data Requirements

No new external data is required. The task depends on a full text inventory of in-repo wording that conflicts with the corrected identity.

Risks

HIGH: Editing checkpoint files or runtime state would falsify historical records and violate the repo's checkpoint immutability rules.
Mitigation: Update current canonical and active files only; leave docs/memory/checkpoint_* and most .awos/ history untouched.
MEDIUM: Repo-wide search-and-replace could erase legitimate benchmark material where CI repair is still a useful coding-agent workload.
Mitigation: Keep CI-specific capability docs where they still serve as benchmarks or proof artifacts, but remove any claim that CI Rescue is the main project identity.

Open Questions

  • Which older GTM/product docs should be repurposed into engineering-pathway docs versus marked historical/deprecated.
  • How much of the existing “compounding” language should remain as a performance effect versus be replaced by the clearer “failure-driven self-learning” framing.
