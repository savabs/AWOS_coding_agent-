Planning & Exploration v1

phase/1 · topic/planning-exploration · active · 2026-07-29

Research question

How should AWOS turn a natural-language coding goal into a grounded, atomic plan without making the model guess file locations, dependencies, or testable acceptance criteria?

Scope boundary: This slice improves deterministic repository understanding and planner inputs. Execution sandboxing and learned reward/evaluation systems are separate governed slices.

Current architecture

Desired data flow

  1. Normalize the goal into explicit paths, symbols, concepts, and likely test terms.
  2. Build one bounded exploration snapshot: directory tree, candidate files, search hits, structural anchors, dependency/symbol facts, test/config files, and negative evidence.
  3. Pass the same structured snapshot and compact summary to the planner.
  4. Require every plan task to identify a grounded file and an observable acceptance check.
  5. Validate the plan deterministically before execution; reject or repair invalid paths and non-atomic tasks.
  6. Persist exploration and plan evidence so an evaluator can score recall, precision, cost, and downstream correctness.

Evaluation contract

Plan quality is not judged by prose. A plan is useful only if it leads to a correct repository state with bounded cost and auditable evidence.

Experiment design

Use deterministic local fixtures first, then a frozen set of realistic repository tasks. Each task runs multiple trials when a live model is involved. Report per-task results and aggregate confidence intervals; never hide failures behind a mean score.

  • Fixture classes: single-file edit, cross-module change, existing-test repair, ambiguous request, non-Python repository, and no-match/invalid-goal case.
  • Baselines: current exploration path, repo-map path, and the upgraded unified path.
  • Ground truth: manually reviewed target files, relevant dependencies, acceptance tests, and forbidden files for each fixture.
  • Score rule: final correctness is a gate; among correct runs, compare recall, retries, cost, latency, and evidence completeness.
  • Anti-gaming: do not award credit for scanning the entire repository; cap files, bytes, tool calls, and wall time.

Risks and decisions

Risk: A larger context can increase cost and distract the planner.
Decision: Keep the snapshot structured, ranked, bounded, and measurable; do not dump the repository.
Risk: Keyword grep misses semantic relationships or non-Python code.
Decision: Preserve deterministic search but add explicit path/symbol extraction and use existing structural/dependency indexes; language-specific expansion is measured, not assumed.
Risk: A planner can satisfy schema while producing a bad plan.
Decision: Plan schema validation is necessary but final tests and fixture-level graders are authoritative.

Conclusion

AWOS should unify exploration and repo mapping into a bounded, replayable planner-input contract, validate plans before execution, and evaluate the full chain from goal to repository state. This is the smallest useful step toward Cursor/Hermes-level repository grounding without prematurely adding model complexity.
