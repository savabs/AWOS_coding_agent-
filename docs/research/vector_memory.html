Vector Memory — Semantic Codebase & Session Retrieval

doc/research phase/6 topic/vector-memory DRAFT 2026-05-19

Current State

AWOS has three retrieval mechanisms today, all lexical (zero semantic understanding):

  • SymbolIndex — AST-extracted class/function names sent raw to Planner. No ranking, no relevance filtering.
  • ExampleStore — exact task_id lookup of past SEARCH/REPLACE pairs. No fuzzy matching.
  • ProjectPlanner Jaccard — keyword overlap for goal deduplication. Fails on paraphrase ("add auth" ≠ "implement login").

Impact of no semantic retrieval

  • Worker receives up to 40 raw symbols regardless of relevance → noise in prompt.
  • Cross-session recall is 0% for semantically similar but lexically different goals.
  • Past successful examples are not retrieved on retry unless task_id matches exactly.
  • ExampleStore can't surface "add rate limiting" when current task is "add throttling".

Research Findings

Dense retrieval vs sparse retrieval for code

VERIFIED (arXiv:2510.04905, Oct 2025): Dense (vector-based) retrieval using neural embeddings outperforms sparse/BM25 retrieval for repository-level code generation tasks. The survey classifies retrieval into: identifier matching → sparse → dense → graph → hybrid. Dense + graph hybrid achieves best results but at higher complexity cost.

VERIFIED (arXiv:2510.04905): "Non-graph-based RAG approaches… now incorporate additional contextual signals, such as file paths, surrounding code blocks, dependency metadata… This evolution has transformed non-graph-based retrieval into a sophisticated and adaptable framework."

Embedding model selection

VERIFIED (HuggingFace model card, ChromaDB docs): all-MiniLM-L6-v2 is ChromaDB's default embedding function. Maps text to 384-dim vectors. Max 256 tokens per chunk. Runs locally with no API cost. Inference: ~5ms per chunk on CPU. Suitable for code snippets and task descriptions.

ChromaDB as the vector store

VERIFIED (ChromaDB docs, realpython.com): chromadb.PersistentClient(path=…) persists collections to disk. Supports SentenceTransformerEmbeddingFunction natively. API: collection.add(documents, metadatas, ids) and collection.query(query_texts, n_results, where). Metadata filtering allows scoping queries by file path, status, or session.

What Cursor does (semantic code search)

VERIFIED (semantic code search article): Cursor embeds code chunks with start/end line numbers + file paths stored in a vector DB. On @Codebase query, it retrieves the top-k relevant chunks and injects them into the prompt. This is the baseline we're replicating locally.

Key limitation

VERIFIED (arXiv:2510.04905 §5.1): "Context window constraints and long-range dependency modeling remain a fundamental bottleneck. Although RAG frameworks partially alleviate this issue by retrieving relevant content externally, the retrieved information often fails to fully preserve semantic continuity across distant code segments."

UNVERIFIED: Whether top-5 chunks at 256 tokens each (1280 tokens total) is the right budget for AWOS's DeepSeek-based Worker. Needs empirical validation after implementation.

Proposed Solution

A new module scaffold/agent/vector_memory.py with two ChromaDB collections stored at .awos/vector_db/:

CollectionWhat is indexedUsed by
codebase_chunksPython AST chunks (function bodies, class bodies) with file+line metadataWorker prompt injection
session_memoryPast task outcomes: action, file, success bool, critique textProjectPlanner goal matching + ExampleStore supplement

VectorMemory class API

class VectorMemory:
    def __init__(self, persist_dir=".awos/vector_db")
    def index_codebase(self, root: str) -> int           # returns chunks indexed
    def query_code(self, query: str, top_k=5) -> list[CodeChunk]
    def store_outcome(self, task: dict, success: bool, critique: str = "") -> None
    def query_outcomes(self, description: str, top_k=3) -> list[OutcomeRecord]
    def find_similar_goal(self, description: str, threshold=0.82) -> str | None
    def reset_codebase_index(self) -> None

CodeChunk dataclass

@dataclass
class CodeChunk:
    chunk_id: str          # sha1(file_path + start_line)
    file_path: str
    start_line: int
    end_line: int
    text: str              # raw source text
    symbol_name: str       # function/class name or ""
    score: float           # cosine similarity to query (0..1)

Integration points

  1. Orchestrator.execute_feature() → call vector_memory.index_codebase(codebase_root) before planning. Incremental: skip files unchanged since last index (mtime check).
  2. Worker.execute_task() → accept vector_chunks: list[CodeChunk] param, inject top chunks into prompt as [RELEVANT CODE] section.
  3. Orchestrator._execute_single_task() → call vector_memory.query_code(task["action"]), pass result to worker.
  4. Orchestrator._execute_single_task() (post-task) → call vector_memory.store_outcome(task, verify_success, critique).
  5. ProjectPlanner.load_or_create_goal() → try vector_memory.find_similar_goal(description) first; fall back to Jaccard if VectorMemory unavailable.

Chunking strategy

Extract via AST: each top-level def or class body becomes one chunk. For files with no top-level symbols, fall back to 50-line sliding windows with 10-line overlap. Max chunk size: 256 tokens (MiniLM limit). Skip __pycache__, .git, generated files.

Incremental indexing

Track per-file mtime in .awos/vector_db/mtime_cache.json. On index_codebase(), only re-embed files modified since last index. Delete+re-add changed file chunks. This keeps indexing fast on subsequent calls (<100ms for a 50-file repo).

Similarity threshold for goal matching

Cosine similarity threshold of 0.82 for find_similar_goal(). Higher than Jaccard (0.4) because embedding space is denser — a 0.82 cosine score corresponds to strong semantic overlap. Configurable via GOAL_SIMILARITY_THRESHOLD constant.

Graceful degradation

If chromadb or sentence-transformers are not installed, VectorMemory raises VectorMemoryUnavailableError. All callers catch this and fall back to the existing non-vector paths (Jaccard, raw symbol list). Zero regressions if deps missing.

Data Flow

execute_feature(goal)
  │
  ├─ vector_memory.index_codebase(root)        ← AST parse → embed → store in codebase_chunks
  │     (incremental, skips unchanged files)
  │
  ├─ project_planner.load_or_create_goal(goal) ← vector_memory.find_similar_goal(goal)
  │     → cosine ≥ 0.82 → reuse existing graph
  │     → cosine < 0.82 → create new graph (fallback: Jaccard)
  │
  ├─ planner.plan(goal, existing_goal=graph)   ← filters completed tasks
  │
  └─ for each task:
        _execute_single_task(task)
          │
          ├─ chunks = vector_memory.query_code(task["action"], top_k=5)
          │           → ChromaDB cosine search on codebase_chunks
          │
          ├─ worker.execute_task(task, vector_chunks=chunks)
          │           → [RELEVANT CODE] section injected into prompt
          │
          └─ (post-task) vector_memory.store_outcome(task, success, critique)
                        → upsert into session_memory collection

Risks & Mitigations

First-run indexing slow on large codebasesMediumIncremental mtime cache; async indexing option in future

Stale index after file deletionsLowreset_codebase_index() + full re-index if collection metadata mismatch
session_memory grows unboundedLowCap at 10,000 documents; evict oldest on overflow
Cosine threshold too tight → no goal matchLowLog miss; fall back to Jaccard; threshold configurable

Edge Cases

  • Empty codebase (no .py files) → index_codebase returns 0, no error.
  • File with syntax errors → skip that file, log warning, continue.
  • Query with no results above threshold → return empty list (worker falls back to raw symbols).
  • ChromaDB collection already exists on restart → get_or_create_collection is idempotent.
  • Concurrent writes from parallel task execution → ChromaDB handles WAL; not a concern at AWOS scale.
