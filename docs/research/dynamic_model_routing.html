Research: Dynamic Multi-Provider Model Routing

Date: 2026-07-27

Status: Research complete; implementation not started.

Question

How should AWOS route coding-agent requests dynamically across OpenAI, Anthropic, DeepSeek, OpenCode Go, OpenRouter, and future providers when only some credentials and models are currently available?

Executive conclusion

AWOS

should build a custom routing authority on top of provider adapters and existing AWOS learning systems. External infrastructure such as LiteLLM is useful for transport

, retries, cooldowns, health, and provider normalization, but it must not own AWOS truth, task success, or the learned routing objective.

The router should be a hybrid capability-aware contextual bandit:

  1. Build a registry of candidate model deployments and their capabilities, prices, limits, and credential requirements.
  2. Resolve runtime capability before selection: supported, configured, healthy, budget-eligible, and task-compatible.
  3. Apply hard constraints before learning
. An unavailable provider must never be selected by LinUCB, Thompson sampling, or a heuristic fallback.
  • Score eligible candidates using task context, predicted quality, cost, latency
    • , reliability, and exploration value.
  • Update the policy only from recorded evidence: verifier/test outcomes
    • , latency, cost, retries, and user/benchmark feedback.
  • Record the routing decision and excluded candidates so the choice is auditable.

    External findings

    1. RouteLLM: trained quality/cost routing

    RouteLLM provides routers trained from preference data and routes between a stronger and weaker model using a calibrated cost threshold. Its documentation emphasizes that thresholds should be

    calibrated against workloads similar to production traffic, and that the framework can use multiple provider types through LiteLLM. This is strong evidence for learned quality/cost routing, but its pretrained pairwise routers are not sufficient as AWOS's complete policy because AWOS has coding-task verification, changing candidates, credential-gated providers, and online feedback.

    Source: RouteLLM repository · RouteLLM paper.

    2. LiteLLM: operational routing infrastructure

    LiteLLM documents load balancing, retries, cooldowns, fallbacks, timeouts, budget routing, health-check-driven routing, and adaptive/complexity routing. Its health-check documentation distinguishes hard failures from transient

    429/408 conditions and supports cooldown thresholds. These are valuable operational patterns. AWOS can use the concepts or optionally an adapter later, but an external router must remain below the AWOS policy layer because it cannot know whether a coding task was actually fixed.

    Sources: routing and load balancing · health-check-driven routing.

    3. Contextual bandits:

    online selection under partial feedback

    Recent routing research frames model choice as a contextual-bandit problem: AWOS observes a task context, selects one model, and receives feedback only for the selected model. The AAAI work on online multi-LLM selection describes budget

    -aware and position-aware LinUCB extensions. The EMNLP 2025 PILOT work aligns query/model representations and adds an online cost policy modeled as a multi-choice knapsack problem. MixLLM similarly combines query tags, quality/cost predictors, a meta-decision maker, and continual learning.

    Sources: AAAI online multi-LLM selection

    · PILOT: Adaptive LLM Routing under Budget Constraints · MixLLM.

    4. Provider capability discovery

    OpenAI documents a GET /models endpoint returning model identifiers and ownership/availability metadata. Anthropic documents a Models API for listing available models and model capabilities. OpenCode Go documents a model endpoint and warns that its curated model list may change. These APIs

    can inform registry refresh and diagnostics, but listing a model is not the same as proving the account can successfully call it; credential presence and actual call health remain separate state.

    Sources: OpenAI List Models · Anthropic List Models · OpenCode Go.

    Candidate record

    Each candidate should have a stable internal candidate_id independent of provider model IDs. Its record should include provider, model ID, endpoint adapter, credential environment variable(s), task capabilities, context/output limits, price

    metadata, expected latency, health state, cooldown state, and policy tags. Provider model IDs must be configuration data, not scattered constants.

    Capability state

    Keep these states separate:

    • SUPPORTED: AWOS has an adapter for the provider.
    • CONFIGURED: required credentials and endpoint configuration are present.
    • DISCOVERED: provider model metadata was observed.
      • >HEALTHY: recent call or health check succeeded.>
    • COOLDOWN: temporarily excluded after classified transient failures.
    • BLOCKED: explicitly disabled by policy or permanent auth/configuration failure.
    • UNKNOWN: not yet checked; eligible only under an explicit probe policy.

    A missing key should produce NOT_CONFIGURED, not a guessed API call. A 401 should not be treated like a timeout. A 429 should normally cause bounded cooldown, not permanent removal.

    Routing objective

    For task context x and eligible candidate a>, define utility as a constrained estimate:

    U(x,a) = quality_estimate(x,a)
         - λ_cost · expected_cost(a)
         -
     λ_latency · expected_latency(a)
         - λ_failure · failure_risk(x,a)
         + exploration_bonus(x,a
    )

    The selected candidate must first satisfy hard constraints: configured credentials, healthy/not-cooldown state, task capabilities, context window, budget, rate limits, and user/project policy. The learned score must never override those constraints.

    Assumptions: only the selected model receives direct outcome feedback; quality observations are noisy and delayed; provider health is nonstationary; candidate sets can change.

    Numerical concerns: clamp rewards, use stable feature normalization, avoid inverse matrices without regularization, and persist policy version/action mappings with every decision.

    Evidence-backed reward

    For coding tasks, the strongest automatic signals are edit application, parser/verifier result, targeted tests, regression tests, latency, token/cost usage

    , retry count, and rerun outcomes. Model confidence and textual self-evaluation may assist ranking but must not be the sole success reward and cannot create debugger PROVEN status.

    Recommended

    implementation phases
    1. Registry and capability snapshot: replace scattered provider/model constants with stable candidate records and credential/configuration status. Do not make live calls yet.
    2. Hard eligibility gate: filter candidates before every call; record excluded candidates and reasons.
    Keep OpenCode Go as the only currently configured candidate without banning future providers.>
  • Provider health state: classify auth, rate-limit, timeout, server, and malformed-request failures; add cooldowns and recovery. Avoid a network probe before every request.
  • Dynamic candidate-aware router: adapt LinUCB/Thompson actions to stable candidate IDs and mask unavailable candidates. Preserve deterministic heuristic fallback for cold start.
  • Quality/cost calibration: build an AWOS coding benchmark and compare static, heuristic, bandit, and optional RouteLLM-style baselines.
  • Observability and user controls: expose selected candidate, excluded candidates, policy reason, estimated cost/latency, and fallback chain in the evidence surface.

    • Research decision

    Do not add a new routing dependency or hard-code a single provider now. First implement an AWOS-owned candidate registry and capability gate, then adapt the existing contextual-band

    it machinery to dynamic candidate IDs. Use LiteLLM concepts as an optional provider/health adapter and RouteLLM as an evaluation/prior baseline, while keeping AWOS's evidence-backed verifier outcomes as the learning truth.
