Verified In-Repository Findings

  • The OpenCode Go endpoint is already configured in fixed_provider.py; no new client dependency is required.
  • The OpenCode Go client uses the OpenAI-compatible >chat.completions.create() seam in existing production code.
  • Existing Qwen references use the exact identifier qwen3.7-plus.
  • The advanced Planner currently requires Anthropic credentials, which caused the provider mismatch in the earlier live-trial design.
  • Native graph validation is independent of the provider and can be regression-tested with mocked OpenCode responses.

Cost and Role Boundary

Qwen is the advanced project planner, not the atomic worker. DeepSeek Pro remains the worker model. This preserves the responsibility boundary even though both calls use OpenCode Go.

Risks

  • OpenCode Qwen responses may use a different response shape than Anthropic; parse only the existing OpenAI-compatible message content and fail closed on empty/malformed output.
  • Structured JSON schema parameters supported by the Anthropic client cannot be copied blindly into OpenAI-compatible requests; use the existing JSON-object request contract and deterministic AWOS validation.
  • Planner cost telemetry must use Qwen pricing, not Sonnet pricing or DeepSeek pricing.
  • Fallback behavior must remain explicit: if Qwen planning fails, CheapPlanner may use DeepSeek Pro as fallback, and the result must identify that fallback.

Non-goals

  • No change to worker model selection.
  • No change to the native graph schema.
  • No new dependency.
  • No live provider call during implementation tests.
  • No automatic retry that hides planner provider failures.
