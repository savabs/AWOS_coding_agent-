Chat Prompt Fidelity

Status: active · Phase: 1 · Observed: 2026-07-27

Research question

Why can the Electron chat experience appear disconnected from the exact text a user entered, and how can AWOS expose the transformation from raw input to provider request to rendered response?

Scope boundary: This is a chat observability and context-continuity problem. It is not a request to improve the model's strategic answer about AWOS's moat.

Current architecture

  • gui/static/chat.js reads the textarea value, trims it, sends message, mode, and chat_id to /api/chat/stream, and renders saved user content.
  • gui/server.py routes the request to GuiChatService.handle_message_stream().
  • scaffold/agent/gui_chat.py stores chat sessions in .awos/gui_chat/, builds QA prompts, selects the provider, and emits streaming metadata.
  • _conversation_messages() exists and excludes the just-appended message, but the OpenCode Go branch currently constructs only a system message and a new user message.
  • gui/static/shared.js applies lightweight Markdown formatting to visible message content. It does not replace ordinary words such as not with now.

Verified data flow

  1. User enters text in #chat-input.
  2. sendMessage() trims it and posts the raw value as message.
  3. GuiChatService appends the raw value to the chat session.
  4. _build_qa_prompt() adds project context and the question label.
  5. OpenCode Go receives messages=[system,user] rather than the full session message list.
  6. The provider response is streamed and saved as the assistant message.
  7. The UI renders stored message content, but does not expose the provider prompt or transformation stages.

Observed incident

Chat record .awos/gui_chat/chat_ab963c5a.json preserves the exact input:

lets not tell me whats the most important moat of this project

The assistant response begins by assuming that not means now. The saved record reports mode=auto, handler=qa, model=qwen3.7-plus, and memory_turns=0. The raw user message was not rewritten in storage; the user cannot currently see the prompt/context boundary that led to the interpretation.

Key findings

  • Input preservation: the saved user content is exact.
  • Rendering: the current Markdown renderer changes formatting only; it is not the source of semantic word substitution.
  • Provider continuity: the OpenCode Go request path omits prior chat turns despite the service's session-memory design.
  • Observability: the UI shows the final response but not a distinct raw-input, normalized-input, provider-prompt, or interpretation view.
  • Mode: the incident was routed to QA, not the coding-agent execution path.

Risks

High: Users cannot distinguish their exact request from provider interpretation.
Mitigation: Preserve and render raw input separately; expose provider prompt metadata without exposing hidden chain-of-thought.
Medium: Adding full prompts to every message can expose secrets or create excessive UI noise.
Mitigation: redact secret-like values, show a collapsed developer-only trace, and expose structured metadata rather than private reasoning.

Research conclusion

The first fix should establish a glass-box message contract: raw user input is immutable, provider request context is inspectable in a bounded trace, interpretation is labeled as interpretation, and the OpenCode path receives the intended conversation history. This strengthens AWOS's evidence-first interface without coupling the kernel to one provider.
