Research: Evaluation Live Adapter

phase/2 · topic/evaluation · active · 2026-07-29

Scope

Connect the real Orchestrator.execute_feature to evaluation_v1 without changing the orchestrator’s task semantics or weakening its existing test/safety gates.

Observed boundary

  • execute_feature(goal, codebase_root, pre_planned_tasks, ...) runs the real plan/edit/verify/test/recovery loop.
  • The returned result includes success, task counts, execution log, errors, elapsed time, debug session ID, and optional worktree path.
  • Focused tests already use deterministic model-boundary patches, so an adapter can be tested offline without provider calls.
  • The evaluator already owns a fresh workspace and independent acceptance commands; the live adapter must not trust the orchestrator’s self-reported success as the correctness oracle.

Design decision

Use a callback adapter around the real orchestrator. Acceptance tests remain evaluator-owned and run after the orchestrator returns. The orchestrator result becomes trajectory evidence, not the hard correctness verdict.

Held-out corpus design

Add small fixtures covering basic edit, exploration, multi-file change, recovery, and safety. Public fixtures validate the harness; a separate holdout manifest must not be used for prompt or reward tuning. Each fixture has an independent acceptance command and allowed-path policy.

Risks

  • Orchestrator may write runtime evidence inside the workspace → exclude evaluator metadata paths or allow them explicitly without allowing source escape.
  • Live model calls make tests nondeterministic → unit tests patch the orchestrator boundary; live runs are opt-in.
  • Self-reported success may disagree with hidden tests → acceptance remains authoritative.
  • Multiple tasks may modify several files → fixture allowed paths must list all intended paths and grader checks the complete diff.
