Research: Live Event Streaming for Agent UX

doc/research phase/4 topic/live-streaming topic/agent-ux 2026-07-05

Problem

The AWOS web UI (agent.html) currently shows a static dashboard with session history. It has an SSE endpoint but it only polls RuntimeSessionStore every 500ms for basic stats (is_running, progress %, cost). Users cannot see live agent output — they cannot watch tasks being executed, files being edited, or model routing decisions being made in real-time.

This is the #1 UX gap vs Cursor/Claude Code/OpenHands. Those products show you the agent working as it works. Our product is a glass box (VISION.md) — we must show every decision transparently.

Current State

What exists

  • GuiEventBus in gui_events.py — a dataclass + event bus with emit() and subscribe(). Writes events to .awos/gui/<id>/events.jsonl. But nothing calls it. It's dead code.
  • gui/server.py has an SSE endpoint /api/agent/stream that polls RuntimeSessionStore every 500ms. Only returns basic stats, not structured events.
  • gui/static/agent.html has a terminal panel, progress bar, stats sidebar, session history, diff viewer, and chat view — all static. SSE only updates progress bar + cost numbers.

Architecture constraint

The orchestrator runs in a separate process from the web server. They cannot share an in-memory queue. Any IPC mechanism must be cross-process.

Architecture Decision: File-Polling via GuiEventBus

orchestrator.py gui/server.py agent.html GuiEventBus SSE endpoint Browser │ │ │ ├─ emit("session_start") │ │ ├─ emit("plan_generated") │ │ ├─ emit("model_routed") │ │ ├─ emit("task_start") ──────→│ .5s poll events.jsonl │ ├─ emit("file_edit") │ for this session │ ├─ emit("test_result") │ send new lines as SSE ───→│ render event ├─ emit("task_complete") │ "data: {event}\n\n" │ by type └─ emit("session_done") │ │ │ │ │ ▼ │ │ .awos/gui/<id>/ │ │ events.jsonl │ │

Why file-polling wins:

  1. Cross-process by nature — orchestrator writes, SSE reads. No shared memory needed.
  2. Persistence — every event lives forever in .awos/gui/. Free session replay.
  3. Simple — GuiEventBus already has emit(), just need to call it.
  4. Fast enough — local file, OS cache, 500ms poll → effectively real-time.

Alternative considered: HTTP callback

Orchestrator POSTs events to http://localhost:8765/api/ingest. Rejected because:
— Requires server to be running first (ordering dependency)
— Extra HTTP overhead for each event
— Server crash = lost events

Event Schema

Event typeWhen emittedKey payload fields
session_start Start of execute_feature() goal, session_id, codebase_root
codebase_indexed After vector memory index n_chunks, elapsed
plan_generated After planner returns tasks n_tasks, tasks: [{id, action, complexity, file}]
model_routed After EscalationEngine decides model model_name, tier, reason, cost_estimate, provider
task_start Before each task execution task_id, action, file, model_name, model_reason
file_edit After file modification path, status, lines_added, lines_removed, diff
test_result After test run test_name, passed, duration, output
task_complete After task finishes task_id, success, cost_usd, n_edits, error
session_done End of execute_feature() completed, failed, total_cost, elapsed

Risk Assessment

RiskMitigation
File polling too slow for real-time feel500ms poll on local file is effectively instant (OS cache). We can drop to 200ms if needed.
events.jsonl grows unboundedRotate at 10K lines. Or keep forever — sessions are bounded per run.
Orchestrator crashes mid-run, events lostEach event is written to disk immediately via GuiEventBus.emit(). Only the last ~500ms of unflushed data is lost.
Web server not running when orchestrator startsEvents accumulate in events.jsonl. SSE picks them up when server starts. No ordering dependency.
Multiple sessions writing to same events.jsonlEach GuiEventBus instance uses session_id as subdirectory: .awos/gui/<id>/events.jsonl
