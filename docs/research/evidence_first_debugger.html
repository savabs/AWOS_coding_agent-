Research: Evidence-First Debugger

doc/research phase/1 topic/evidence-first-debugger active 2026-07-26

Current Architecture

AWOS already has several strong debugging primitives, but they are split across different runtime artifacts and UI surfaces. Today the repo can record what happened; it cannot yet make a disciplined claim about what issue is proven, what is only a hypothesis, and what remains unknown.

Research conclusion: AWOS should build a custom evidence-first debugger core on top of OpenTelemetry + OpenInference style telemetry concepts, while keeping AWOS itself as the authority on truth classification. External backends may visualize or store telemetry, but they should not decide whether an issue is proven.

Current Data Flow

  1. The orchestrator executes tasks and emits structured UI events through GuiEventBus, which appends to .awos/gui/<session>/events.jsonl.
  2. Task-level quantitative facts are separately written as TaskSpan records to .awos/spans.jsonl.
  3. Improvement-oriented task/session analytics are separately written as TaskTelemetry / SessionTelemetry to .awos/telemetry.jsonl.
  4. gui/server.py tails the most recent session file by byte offset and streams events to the frontend over SSE. If the subprocess exits without session_done, the server emits a synthetic error event.
  5. gui_chat.py and agent.html render the event stream, but currently the UI is a viewer of low-level events rather than a debugger with truth classes, cause chains, or proof bundles.
  6. FaultLocalizer can rank likely fault locations, but its output is currently heuristic context for the worker, not a canonical debugging artifact.

Architecture Direction

The debugger should not replace the current stores. It should sit above them as a unifying interpretation layer:

runtime artifacts  →  normalized debug evidence  →  finding / report engine  →  rerun / validation  →  UI + exports

spans.jsonl        →  evidence items             →  PROVEN / HYPOTHESIS / UNKNOWN
telemetry.jsonl    →  evidence graph             →  root-cause attribution
ui events.jsonl    →  artifact bundle            →  proof-by-rerun decisions

Observations

These are concrete findings from the current repo and from external research. They are the basis for the debugger plan.

Key Findings

  • AWOS already uses append-only evidence stores. ObservabilityStore appends JSONL task spans, and GuiEventBus appends per-session event journals. This is a strong base for a debugger because append-only records preserve causality and post-hoc auditability.
  • Crash evidence is already partially first-class. gui/server.py detects subprocess death without session_done and emits a synthetic error event. That means AWOS already has one concrete pattern where runtime behavior is converted into a user-visible failure fact.
  • TaskTelemetry is richer than the UI event stream. It already captures verify_passed, verify_attempts, retry_count, failure_stage, failure_reason, test counts, diff stats, and stage traces. This is exactly the kind of structured evidence a debugger should consume.
  • FaultLocalizer is useful, but heuristic. Its own design is confidence-based and combines stack-trace mentions, vector similarity, keyword matching, and recency. This makes it good for ranking likely root causes, but not for proving truth.
  • Schema drift already exists between event producers and consumers. LiveRenderer and older specs reference names like planning_done, worker_start, worker_done, verify_result, task_done, and retry_notice; GuiEventBus currently defines plan_generated, test_result, task_complete, session_done, and error. gui_chat.py still formats several legacy names. A debugger cannot be trusted without a canonical event/evidence schema.
  • The current UI is a trace viewer, not yet a debugger. It can show model routing, tool calls, file edits, test results, and session completion, but it cannot currently answer: “what issue is proven, by which evidence, at which stage, with what confidence, and did rerun confirm it?”
  • External tooling consistently separates tracing from judgment. OpenTelemetry and OpenInference standardize telemetry transport and semantics; Phoenix, Langfuse, and Logfire visualize traces; Laminar emphasizes replay/rerun loops; AgentDebugX adds diagnose → attribute → recover on top of traces. None of them alone solves AWOS’s truth-classification problem.

Math / Algorithm Survey

The debugger should use two separate computations:

  1. Truth classification — deterministic whenever possible.
  2. Investigation ranking — probabilistic/heuristic, but never allowed to claim proof by itself.

Recommended first-phase truth model:

status(finding, evidence_set) =
  PROVEN      if ∃ deterministic proof rule that fires on recorded evidence
  HYPOTHESIS  if no proof rule fires and investigation_score ≥ τ
  UNKNOWN     otherwise

Recommended first-phase ranking model:

investigation_score =
  w1 * stack_trace_match
+ w2 * verifier_or_test_alignment
+ w3 * fault_localizer_rank
+ w4 * recent_edit_overlap
+ w5 * repeated_failure_prior
+ w6 * stage_consistency

Important constraint: investigation_score is used only to order what AWOS looks at next. It must never upgrade a finding from HYPOTHESIS to PROVEN without a proof artifact.

First-phase proof rules should be simple and auditable, for example:

  • nonzero subprocess exit with captured stderr/output
  • verifier rejection with recorded issue list
  • failing test with traceback
  • syntax/parser/import error raised by a real toolchain
  • failed edit application where the exact search/replace or patch mismatch is recorded

Only after the deterministic layer is stable should AWOS consider learned or LLM-assisted attribution. Even then, those systems should emit hypotheses and rerun plans, not truth directly.

Frozen Planning Decisions

  • Claim scope is mandatory. A recorded failing test can prove that the test failed; it does not automatically prove which file, symbol, model decision, or edit caused the failure.
  • Proof is claim-scoped. PROVEN applies to a specific claim backed by named evidence and a versioned rule, never to an entire session or broad narrative.
  • Evidence absence is not evidence of success. Missing, truncated, redacted, or contradictory inputs produce an evidence gap and may result in UNKNOWN, not an invented conclusion.
  • Rerun evidence is additive. A divergent rerun cannot silently erase an earlier observation; it creates a new validation record linked to the original finding.
  • Attribution remains separate. FaultLocalizer, scores, LLM judgments, recency, and similarity can rank investigation work but cannot satisfy a proof rule by themselves.

Adopted External Concepts

  • OpenTelemetry should be the base model for spans, logs, metrics, exceptions, and exporters.
  • OpenInference should provide the semantic categories for AGENT, LLM, TOOL, EVALUATOR, and related spans.
  • Phoenix / Langfuse / Logfire are good visualization or backend candidates, but none should become the source of truth for issue classification.
  • Laminar contributes the strongest replay-loop idea: read trace → change system → rerun from a cached or checkpointed boundary → compare.
  • AgentDebugX contributes a useful pipeline vocabulary: detect → attribute → recover → rerun, but AWOS should keep its own runtime-native implementation.

Risks

HIGH: Heuristic attribution could be mistaken for proof.
Mitigation: Keep truth classification separate from ranking. No confidence score, localizer output, or LLM judgment may produce PROVEN on its own.
HIGH: Dual event vocabularies can make the debugger internally inconsistent.
Mitigation: Introduce a canonical event/evidence schema plus explicit legacy adapters. Add compatibility tests so old and new session artifacts normalize to one model.
HIGH: Replay/rerun can become misleading if nondeterminism is ignored.
Mitigation: Treat reruns as additional evidence, not perfect replay magic. Record enough context to explain the rerun boundary, environment, and divergence.
MEDIUM: Prompt/tool content capture may leak sensitive data.
Mitigation: Define content-redaction settings from day one. Separate structural telemetry from raw content capture.
MEDIUM: Raw telemetry volume may grow quickly.
Mitigation: Keep append-only stores, but add report bundling, retention policies, and summary views so the debugger reads normalized artifacts rather than rescanning everything every time.
MEDIUM: UI trust could improve slower than backend truth quality.
Mitigation: Make the first debugger surfaces simple: show finding status, evidence references, and rerun result before building advanced visualizations.

Open Questions

  • Must resolve before implementation: What is the canonical on-disk debug bundle format under .awos/debug/, and how does it link sessions, tasks, evidence, findings, and reruns?
  • Must resolve before implementation: What is the minimum checkpoint granularity for proof-by-rerun: whole session, task boundary, or per-event?
  • Can resolve during implementation: Should AWOS dual-write native debug bundles and OTel/OpenInference spans immediately, or first build native bundles and add external export later?
  • Can resolve during implementation: Which CLI and UI surfaces are mandatory in phase 1, and which can wait until the backend truth model is validated?
  • Can resolve during implementation: How much raw prompt/tool/request content should be stored by default, and what redaction or opt-in settings are needed?
