Research: ReflexionMemory — Phase 5B

phase-5b verbal-rl error-pattern-store critique-injection Research Complete 2026-05-19

Problem Statement

AWOS retries failing tasks via SelfCorrectionEngine, which classifies errors into 4 buckets and injects static hardcoded hints. This has three hard limitations:

  • No cross-session memory — AWOS forgets every failure on restart. The same mistake in api/users.py repeats indefinitely.
  • No task-specific critique — hints like "fix the syntax error" are generic. Reflexion paper proves task-specific verbal critique is 2-3x more effective.
  • No adaptation — static rules cannot learn that e.g. KeyError on dict access is a recurring pattern in this codebase and suggest .get() universally.

Hypothesis

Storing verbal self-critiques in a persistent JSONL store and prepending the top-3 relevant ones to retry prompts will reduce the repeat-failure rate on the same file/error-type pair, improving effective pass_rate without any model weight updates or significant cost increase.

Success metric: Pass rate on retry attempts (attempt 2+) should increase by at least 10 percentage points vs the current static hint baseline, measured on internal test suite runs.

Research Findings

1. Reflexion — Princeton / NeurIPS 2023

VERIFIED (arXiv:2303.11366, NeurIPS 2023): Reflexion agents store verbal self-reflections in an episodic memory buffer. On retry, the Actor (LLM) receives its prior reflections as context. On HumanEval Python: GPT-4 baseline = 80% pass@1. Reflexion + GPT-4 = 91% pass@1. Improvement: +11pp without any weight updates.

Key implementation details from the paper:

  • Three models: Actor (generates code), Evaluator (scores output — can be unit tests), Self-Reflection (generates verbal critique from failure signal).
  • Memory: Short-term = trajectory history (current session). Long-term = episodic store of past self-reflections (persisted).
  • Critique trigger: fired on binary failure signal (test fails) — not on every attempt.
  • Memory cap: max 1 experience per task in the paper — AWOS can use more since we have file+error_type retrieval.
  • Cost: one extra LLM call per failure — the paper uses GPT-4 for self-reflection; AWOS will use Gemini Flash (~/usr/bin/bash.0001/call).

2. Self-Refine — NeurIPS 2023 (arXiv:2303.17651)

VERIFIED (selfrefine.info, NeurIPS 2023): Iterative feedback-refine loop. Key insight: feedback must be (1) localised — identifies the specific line/pattern that is wrong, and (2) actionable — tells the model what to do differently. Retains history of past outputs in prompt. Achieves 5-20% improvement on code tasks vs single-shot.

3. SWE-RL — Meta / NeurIPS 2025 (arXiv:2512.18552)

VERIFIED (facebookresearch/swe-rl, NeurIPS 2025): State-of-the-art self-improving software agent. Uses test execution outcomes as primary reward (we implemented this in Phase 5A). Combines pass/fail reward with trajectory memory. Outperforms human-data baselines on SWE-bench by +10.4% via grounding in mechanical realities of code execution.

Design Options

Option A — Minimal (Recommended)

Add ErrorPatternStore (JSONL). Generate critique via cheap LLM call on failure. Retrieve by (file_path, error_type) exact match. Inject top-3 into worker prompt.

Estimated effort6-8h

Option B — Vector Retrieval

Use VectorMemory (ChromaDB) to store critique embeddings. Retrieve semantically similar past critiques regardless of file path. More powerful but adds ChromaDB dependency cost and ~50ms latency per retrieval.

Decision: Defer to Phase 6. Option A is sufficient to prove the hypothesis. Vector retrieval adds complexity without clear benefit until we have 500+ stored critiques.

Option C — LLM-as-Evaluator

Use LLM to both run tests and judge correctness. Expensive. Not needed: TestRunner (Phase 5A) already provides objective pass_rate. Rejected.

Risks and Mitigations

RISK (Medium): Critique generation adds latency.
One cheap LLM call on failure: ~300-500ms. Only fires on failure, not on every attempt. Mitigation: async fire-and-forget. Critique stored for next attempt, not current one.
RISK (Medium): Hallucinated or misleading critique.
LLM may generate an incorrect explanation. Mitigation: critique is informational only (prepended as a hint, not executed as code). If critique misleads, TestRunner pass_rate still penalises the outcome, and LinUCB escalates model tier.
RISK (High): Prompt bloat degrades performance.
Injecting too many long critiques can push the actual task out of the context window. Mitigation: hard cap of 3 critiques, each truncated to 100 tokens. Total overhead ≤ 300 tokens.
RISK (Low): Stale critiques for refactored files.
A critique for api/users.py written 3 months ago may be irrelevant if the file was rewritten. Mitigation: critiques are hints, not instructions. Still informative about error class patterns. Future: add file hash to ErrorPattern and skip critiques for significantly changed files.
RISK (Low): API call fails during critique generation.
Mitigation: graceful fallback to static SelfCorrectionEngine hint. Never blocks the retry loop.

Verdict

Proceed with Option A (Minimal). The research case is strong — Reflexion's +11pp improvement on HumanEval is replicated across multiple papers. The implementation is low-risk (1 new file, 3 small modifications, graceful fallback). Cost impact is negligible (~/usr/bin/bash.0001 per failure). The hypothesis is falsifiable: we can measure retry pass_rate before and after using the TestRunner reward signal already wired in Phase 5A.
