Research: Token Efficiency with Aider + Claude API

doc/research phase/1 topic/token-efficiency topic/aider topic/caching active 2026-05-13

Why This Matters

GitHub Copilot is moving from credit-based pricing to token-based pricing from June 1, 2026. Every input and output token now directly maps to cost. The prior mental model (1 credit ≈ 1 task) is gone.

The strategic response: migrate to Aider + Claude API, where we have full control over every token. We can cache aggressively, select models per task, compress prompts, and measure everything.

Core equation: Cost = (input_tokens × $input_rate) + (output_tokens × $output_rate)
Cache reads replace fresh input at 10% of the cost. Output tokens cost 5× more than input. So: maximize cache hits, minimize output verbosity.

Key Insight: Where Tokens Come From in Aider

Every Aider request sends:

  1. System prompt — AWOS rules / coding conventions (large, stable → ideal for caching)
  2. Repo map — summary of the codebase (medium, semi-stable)
  3. Read-only files (added with --read) — stable reference context
  4. Editable files (in chat) — changes each turn
  5. Chat history — grows each turn, summarized by weak model
  6. User message — small, always fresh

Items 1–3 are stable — prime candidates for caching. Items 4–6 change frequently.

Cache Economics

Cache read vs fresh input ratio: 10:1 savings
If your system prompt is 2,000 tokens and you make 20 requests per session:
• Without cache: 20 × 2000 × $3.00/MTok = $0.12
• With cache: 1 write × $3.75/MTok + 19 reads × $0.30/MTok = $0.0075 + $0.0114 = $0.019
• 84% savings on that context alone

Cache TTL Options

  • 5-minute TTL (default): 1.25× write cost. Refreshed free when hit. Good for active sessions.
  • 1-hour TTL: 2× write cost. Good when requests are spaced >5 min apart.

Aider uses 5-minute TTL with --cache-keepalive-pings N to prevent expiry (pings every 5 min up to N times).

How Claude Prompt Caching Works

Cache is keyed to the exact prefix up to a cache_control breakpoint. The cache prefix must be 100% identical across requests — any change invalidates it.

Cache Ordering (Claude processes in this order)

  1. tools definitions
  2. system prompt
  3. messages (conversation history)

Changes to tools invalidate all subsequent caches. Changes to system prompt invalidate message cache. Changes to messages only invalidate message cache.

What Can Be Cached

  • Tool definitions
  • System messages (entire system prompt)
  • Text in message history
  • Images and documents in messages
  • Tool results

What CANNOT Be Cached

  • Thinking blocks (cached indirectly as part of conversation, not directly)
  • Empty text blocks
  • Sub-content blocks (citations sub-blocks)

Automatic vs Explicit Caching

ModeHow to useBest for
AutomaticTop-level cache_control: {type: ephemeral}Multi-turn conversations — cache breakpoint moves forward automatically
Explicit breakpointscache_control on individual content blocks (max 4)Fine-grained control; different sections cached at different frequencies

Cache Invalidation Gotchas

Never put dynamic content before a cache breakpoint. Timestamps, per-request context, user messages — these change every call and bust the cache. Put cache_control on the last static block, not on the varying one.
Tool definition changes bust the entire cache. Keep tool definitions stable during a session. Don't add/remove tools between requests.
Growing conversations: use the 20-block lookback window. If a conversation grows by >20 blocks between requests without a mid-conversation breakpoint, you'll miss the cache. Add explicit breakpoints at stable points.

Pre-Warming the Cache

Send a request with max_tokens=0 before users/work begins. This writes the cache without generating output (0 output tokens billed). Do this at session start.

client.messages.create(
    model="claude-sonnet-4-5",
    max_tokens=0,                          # no output generated
    system=[{
        "type": "text",
        "text": CONVENTIONS_TEXT,
        "cache_control": {"type": "ephemeral"}
    }],
    messages=[{"role": "user", "content": "warmup"}]
)

Tracking Cache Performance

Response usage fields to monitor:

  • cache_read_input_tokens: tokens served from cache (cost 10%)
  • cache_creation_input_tokens: tokens written to cache (cost 125%)
  • input_tokens: tokens after last cache breakpoint (cost 100%)

Total input = cache_read + cache_creation + input_tokens

Read-Only Context

Use --read FILE (or /read-only FILE in chat) for files that should be in context but not edited. Aider organizes these separately and they benefit from caching. Don't add files to the editable set unless you plan to edit them — editable files get larger prompts.

Complete Token Efficiency Strategy Map

Strategy 1: Claude Prompt Caching (highest ROI)

  • Enable: --cache-prompts in Aider
  • Savings: 84%+ on system prompt tokens per session
  • Keep warm: --cache-keepalive-pings 3
  • Pre-warm: run scripts/prewarm_cache.py at session start
  • Risk: cache busted if system prompt changes mid-session

Strategy 2: Repo Map Minimization

  • Set --map-tokens 512 (or 0 for single-file work)
  • Maintain lean .aiderignore to exclude docs, HTML, test fixtures
  • Use --map-refresh files not always
  • Savings: repo map can be 1000–3000 tokens per request — this cuts 50–75%

Strategy 3: Context Window Discipline

  • Only add files you plan to edit in this session: /add FILE
  • Drop files when done: /drop FILE
  • Use /read-only for reference files (cached separately, cheaper)
  • Set --max-chat-history-tokens 6144 — history is summarized, not truncated

Strategy 4: Model Tiering

  • Haiku for: commit messages, quick Q&A, boilerplate generation, simple edits
  • Sonnet for: architecture decisions, complex logic, debugging
  • Architect mode for: large multi-file refactors (Sonnet plans → Haiku writes)
  • Never use Opus unless explicitly needed — 10× Haiku cost for marginal gain

Strategy 5: Output Token Minimization

Output tokens cost 5× more than input. Minimize them by:

  • Ask for diffs, not full file rewrites (diff edit format is Aider's default for Sonnet)
  • Avoid "explain your reasoning" unless debugging
  • Use concise conventions file (no verbose prose)
  • Prefer yes/no or code-only responses where possible

Strategy 6: Conventions File Compression

  • The AWOS .github/copilot-instructions.md is ~700 lines. Aider doesn't need all of it.
  • Create CONVENTIONS.md: 50–100 lines of dense, machine-optimized rules
  • Load with --read CONVENTIONS.md (cached, read-only)
  • This single file gets cached on first request and costs $0.30/MTok after that

Strategy 7: Batch API for Non-Urgent Work

  • Anthropic's Batch API gives 50% discount on both input and output tokens
  • Tradeoff: responses take up to 24 hours (async)
  • Use for: code review, documentation generation, test case creation
  • Not suitable for interactive development

Strategy 8: Token Tracking and Feedback Loop

  • Enable: --llm-history-file .aider.llm.history
  • Parse with scripts/token_report.py to get: total tokens, cache hit rate, cost estimate
  • Review weekly — identify which tasks are token-heavy and optimize them
  • Target: cache hit rate > 70% for system prompt tokens

Risk Register

HIGH: Cache invalidation from dynamic system prompt content. If CONVENTIONS.md or tool definitions change mid-session, entire cache busted. Mitigation: freeze CONVENTIONS.md per session. Only update between sessions.
MED: Cache miss on first request. First request always pays write cost (125%). Need >2 requests per session to break even. Mitigation: pre-warm cache at session start with prewarm script.
MED: Haiku quality degradation for complex tasks. Haiku is cheaper but less capable. Wrong model selection can cause retries, costing more. Mitigation: clear task-complexity guidelines. Default Sonnet for all code changes.
