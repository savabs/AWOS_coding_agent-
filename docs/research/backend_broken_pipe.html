Research: Backend Agent Startup Broken Pipe

Status: active · Date: 2026-07-28

Question

Why does a real Electron submission persist Error: [Errno 32] Broken pipe before an orch_* log or runtime session is created?

Verified observations

  • Electron control fill and semantic submit both return status: ok.
  • The UI ledger records chat_response_started and chat_submitted for chat_1f2c9aeb and trace trace_788f3a78e3db469b872faa213e9a675b.
  • The persisted chat result is Error: [Errno 32] Broken pipe; no probe file was created.
  • No new orch_* log or resolvable rs_* session was created.
  • The failure is surfaced by GuiChatService._stream_agent after _run_agent raises.
  • The current code uses OpenCode Go through the OpenAI-compatible client in planner/worker paths; the exact failing write must be isolated with instrumentation or a focused provider mock.

Relevant flow

  1. gui/static/chat.js submits /api/chat/stream.
  2. gui/server.py invokes GuiChatService.handle_message_stream.
  3. scaffold/agent/gui_chat.py starts _run_agent in a thread.
  4. _run_agent constructs Orchestrator and calls execute_feature.
  5. The exception is converted to the persisted assistant error before runtime-session correlation exists.

External source

Python subprocess documentation states that BrokenPipeError can occur when writing to a child process whose pipe has closed, and recommends communicate() for coordinated pipe I/O. This is a diagnostic hypothesis only; the current failure may also come from a network/provider stream or another pipe boundary.

Risks and next evidence

  • Do not catch and hide the exception; preserve boundary, provider, and child return-code evidence.
  • Do not assume the observer is at fault until the failing writer is identified.
  • Next proof: run the smallest direct agent invocation with provider calls mocked, then add temporary structured exception attribution at each external boundary.
