Assistant Live Observer

Status: active · Phase: 1 · Observed: 2026-07-27

Research question

How can an external coding assistant reliably understand what the user is doing in AWOS and what the backend is doing at the same time, without depending on screenshots or confusing a current run with an old session?

Product intent: The AWOS agent is not the problem under investigation. This feature is the observation bridge between AWOS and an assistant listener.

Current architecture

LayerCurrent behaviorGap for an assistant listener
GuiEventBusPersists per-run .awos/gui/<session>/events.jsonl and supports in-process subscribers.Events have no stable event ID, sequence cursor, source, correlation ID, or visibility classification.
gui/server.py/api/agent/events tails the newest session and sends SSE frames.It does not accept a session/filter/cursor, does not emit SSE id, and sends synthetic idle events that can obscure the real timeline.
RendererUses EventSource, loads one manifest plus one event list, and projects events locally.It is a browser view, not a durable observer contract for an assistant or disconnected client.
UI actionsChat and renderer actions are handled in frontend code and chat storage.Submitted prompts, view changes, session selection, and app lifecycle are not in the same correlated event stream.
Runtime/debug stateSession records, manifests, evidence, traces, and chat files are stored separately.There is no single cursor/snapshot that tells an assistant which records belong to the current user action.

Verified observations

  • Electron loads /agent, which serves gui/static/agent.html; that entrypoint is separate from the instrumented gui/static/chat.js chat view.
  • A live Electron smoke check returned 200 from /api/observer/snapshot, but the UI ledger did not receive app_opened, view_changed, or chat_submitted because the actual Electron entrypoint bypasses those hooks.
  • The existing backend correlation path is present: GuiChatService creates a trace and passes chat_id/trace_id into Orchestrator and its event bus.
  • The live renderer already proves that structured events are sufficient to describe plan, routing, tools, edits, tests, evidence, and completion.
  • The current stream chooses the latest session by directory modification time, which can misattribute events when old sessions remain active or multiple runs overlap.
  • SSE is one-way and appropriate for server-to-listener updates, but resumability requires event IDs and replay from a cursor.
  • The current stream emits unnamed data: frames; the browser and a future assistant cannot use Last-Event-ID recovery reliably.
  • OpenTelemetry's context-propagation model supports correlating signals across process boundaries using trace and span identifiers; AWOS needs a smaller local equivalent.

Recommended architecture

  1. Canonical event envelope: add schema version, event ID, sequence, timestamp, source, event type, session/chat/trace correlation, and bounded payload.
  2. Durable event ledger: retain append-only JSONL for replay and a bounded in-memory index for low-latency observation.
  3. Observer API: provide filtered SSE with id, retry, keepalive comments, explicit session/cursor filters, and replay endpoints.
  4. Assistant snapshot: provide a compact read-only snapshot containing current UI action, current run, recent events, task states, files, verification, errors, and cursor.
  5. UI action events: emit meaningful actions such as app open, view change, prompt submitted, session selected, task started, and user approval. Do not emit every keystroke by default.
  6. Assistant adapter: expose a local CLI/tool or future MCP resource that reads snapshots and cursor ranges. Do not make MCP the kernel event contract.

Transport research

  • MDN and the WHATWG HTML Standard define SSE as a UTF-8 text/event-stream with named events, id, retry, keepalive comments, automatic reconnection, and Last-Event-ID recovery.
  • OpenTelemetry documents context propagation as the way to correlate signals across process boundaries using trace/span identifiers. AWOS should use correlation IDs even if it does not adopt the full OpenTelemetry SDK.
  • The MCP transport specification supports JSON-RPC over stdio or Streamable HTTP and documents resumable SSE patterns. MCP is a possible adapter for an assistant-facing tool later, but introducing MCP into the kernel now would add unnecessary coupling.

Risks

High: A listener can receive stale, duplicated, or misattributed events.
Mitigation: Stable event IDs, monotonic per-stream sequence, explicit session filters, cursor replay, and deduplication.
High: Event payloads can leak prompts, secrets, or private reasoning.
Mitigation: assistant-safe event classes, payload bounds, redaction, no raw chain-of-thought, local-only default binding, and explicit opt-in for sensitive content.
Medium: A long-lived SSE connection can fail or multiply across clients.
Mitigation: one observer connection, reconnect with cursor, bounded replay, keepalive, and snapshot fallback.

Research conclusion

The correct building block is not a screenshot pipeline and not a second chat model. It is a durable, correlated, replayable AWOS event contract with an assistant-facing observer adapter. SSE is suitable for live delivery; the durable ledger and cursor make it reliable across disconnects and turns; snapshots let the assistant recover the current truth before reasoning.
