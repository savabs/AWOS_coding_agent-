Research: Fixed OpenCode Go Agent Path

phase/1 · topic/provider-routing · active · 2026-07-30

Decision under research

For the initial working coding-agent product, use OpenCode Go exclusively with the fixed model deepseek-v4-pro. Dynamic routing and other providers remain disabled until the core product is reliable.

Current architecture

ModuleObserved behavior
scaffold/agent/worker.pyCreates an OpenCode Go OpenAI-compatible client when OPENCODE_GO_API_KEY exists, but also initializes other provider clients.
scaffold/agent/cheap_planner.pyUses OpenCode Go but defaults to qwen3.7-plus.
scaffold/agent/goal_clarifier.pyCalls LiteLLM with deepseek/deepseek-chat, which is a direct DeepSeek path rather than OpenCode Go.
scaffold/agent/orchestrator.pyAuxiliary cheap calls hard-code qwen3.7-plus through the OpenCode client; model selection is not centrally fixed.
scaffold/agent/react_worker.pyContains OpenCode, direct DeepSeek, OpenAI, OpenRouter, and Gemini branches.

Verified observations

  • The OpenCode Go health check succeeded with available=true, balance_ok=true, and 23 models returned.
  • The first benchmark trial’s insufficient-balance error came from the direct DeepSeek LiteLLM clarification call.
  • The same trial reached OpenCode Go planning successfully before the planner grounding contract rejected the generated paths.
  • The active product decision is recorded in memories/repo/project_structure.md.

Data flow to change

  1. Load the OpenCode Go credential and base URL.
  2. Construct one fixed OpenAI-compatible client for deepseek-v4-pro.
  3. Use that client/model for clarification, planning, execution, and auxiliary calls.
  4. Reject or bypass alternate provider branches on the active product path.
  5. Record provider/model truthfully in telemetry and evaluation reports.

Risks

HIGH: Leaving a direct-provider fallback can spend against the wrong account or create inconsistent behavior. Mitigation: centralize the fixed provider/model contract and test alternate credentials do not change selection.
MEDIUM: Existing tests may rely on provider fallback branches. Mitigation: update only active-path tests and preserve isolated legacy adapters outside the product path.

Non-goals

  • No dynamic model routing.
  • No provider failover.
  • No new dependency.
  • No live benchmark retry during implementation.
