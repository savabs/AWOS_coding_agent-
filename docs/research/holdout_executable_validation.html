Research: Holdout Executable Validation

Date: 2026-08-01

Observed failure

Controlled7 dry-run accepted an acceptance command whose first token was a relative virtual-environment interpreter. The evaluator changes its working directory to the candidate repository, so the interpreter later resolved incorrectly and acceptance could not launch.

Current flow

  1. scripts/run_holdout_live.py:load_single_fixture validates manifest and repository digests and binds private oracle tokens.
  2. main() calls load_single_fixture, then returns success immediately for --dry-run.
  3. EvaluationRunner._run_acceptance eventually invokes the structured argv from the fixture under candidate CWD.

Root cause

The loader validates acceptance path tokens after the executable but does not validate the executable token itself. Therefore relative, missing, and stale absolute interpreters reach dry-run success.

Decision

Fail closed during fixture loading: each acceptance command must have an absolute executable first token that exists and has execute permission. Keep structured argv and shell-free execution unchanged.

Risks and non-goals

  • Do not resolve relative executables against candidate CWD; that hides malformed fixture metadata.
  • Do not accept a merely existing non-executable file.
  • Do not validate arbitrary command arguments as host executables.

Sources

Primary sources: scripts/run_holdout_live.py, scaffold/agent/evaluation_v1.py, and controlled7 failure evidence. No new dependency or external API is required.
