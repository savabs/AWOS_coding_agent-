Research: ProjectPlanner — Persistent Goal DAG

doc/research phase/5C topic/project-planner active 2026-05-19

Current Architecture — What Exists

AWOS already has three planning primitives. All are stateless and session-scoped: they discard their state when the session ends. ProjectPlanner wraps them with a persistent Goal DAG stored on disk.

Existing Planning Modules

Module / FileRoleLimitation
scaffold/agent/planner.pyOne-shot: user goal → list of atomic tasksEphemeral. Plan discarded after execute_feature() returns.
scaffold/agent/task_decomposer.pyReactive: breaks a failing task into 2-4 sub-tasksOnly fires on retry, no awareness of sibling tasks.
scaffold/agent/dag_executor.pyParallel execution of tasks with declared dependenciesNo persistence; re-built from scratch each session.
scaffold/agent/orchestrator.pyRuns the Planner→Worker→Verifier loop per task_execute_single_task has no access to the outer goal context.

The Goal Amnesia Problem — Data Flow Today

Session 1:
  User: "Add OAuth2 authentication"
  Planner.plan() → [task1, task2, task3, task4]  (ephemeral list)
  Orchestrator runs tasks 1-4
  Session ends → plan GONE

Session 2:
  User: "Add admin-only rate limiting"
  Planner.plan() → [task1, task2, task3]          (NEW ephemeral list)
  Orchestrator has NO knowledge that:
    - OAuth2 middleware (task1 from session 1) already exists
    - admin routes were created during session 1
    - task3 from session 1 failed and was partially patched

Proposed Data Flow With ProjectPlanner

Session 1:
  User: "Add OAuth2 authentication"
  ProjectPlanner.load_or_create(goal="Add OAuth2")
    → Creates .awos/goals/goal_a1b2.json  (DAG persisted to disk)
  Orchestrator runs tasks, updates node statuses in DAG
  Session ends → DAG PERSISTS

Session 2:
  User: "Add admin-only rate limiting"
  ProjectPlanner.load_or_create(goal="Add admin rate limiting")
    → Finds goal_a1b2.json is semantically related
    → Merges: appends 3 new nodes to existing DAG
    → Completed nodes are skipped; pending nodes re-attempted
  Orchestrator runs ONLY the delta

Observations — Key Findings

Finding 1: Orchestrator already has task-level hooks

In orchestrator.py, _execute_single_task() emits success/failure to EscalationEngine.record_outcome(), RewardStore, and updates ErrorPatternStore. These are the exact hooks needed to update a Goal DAG node status. Zero new hooks required — only new consumers of existing events.

Finding 2: TaskDecomposer already splits tasks

When a task hits max_attempts, Orchestrator._execute_single_task() calls self.decomposer.decompose(task) and retries sub-tasks inline. ProjectPlanner can capture these decomposed sub-tasks as new child nodes in the DAG, giving persistent visibility into decomposition history across sessions.

Finding 3: AgentStateManager exists but is not used for goal tracking

scaffold/agent/agent_state_manager.py tracks per-task execution state within a session (checkpointing, resume). It is a good structural analogue for ProjectPlanner, but is scoped to a single execute_feature() call, not to multi-session goals.

Finding 4: No LLM needed for graph operations

Goal matching (is this new request an extension of an existing goal?), node status updates, topological sort, and DAG serialisation are all pure Python operations. LLM is only needed optionally for goal similarity matching (semantic search) — and even that can be replaced by keyword overlap for Phase 5C.

Goal DAG Node Schema

GoalNode {
  goal_id:       str          # UUID, e.g. "g_a1b2c3"
  description:   str          # human-readable, e.g. "Add OAuth2 auth"
  parent_ids:    list[str]    # upstream dependencies (empty for root)
  child_ids:     list[str]    # downstream nodes
  tasks:         list[dict]   # Planner task dicts assigned to this node
  status:        Literal["pending", "in_progress", "completed",
                          "failed", "stalled"]
  created_at:    str          # ISO 8601
  updated_at:    str          # ISO 8601
  completed_at:  str | None
  session_ids:   list[str]    # which sessions touched this node
  failure_count: int          # incremented on each failed attempt
  critique_ids:  list[str]    # ErrorPattern IDs from ReflexionMemory (Phase 5B)
}

Goal Graph File Layout

.awos/
  goals/
    goal_a1b2c3.json   # one file per root goal
    goal_d4e5f6.json
    INDEX.json         # {goal_id: {description, status, updated_at}} — fast lookup

Algorithm — load_or_create_goal()

1. Hash or embed the user request description
2. Scan INDEX.json for all goals with status != "completed"
3. Compute keyword overlap score between request and each open goal
4. If best score >= MATCH_THRESHOLD (0.4):
     Load that goal graph → append new tasks as child nodes
   Else:
     Create new goal graph with request as root node
5. Persist to .awos/goals/{goal_id}.json
6. Return GoalGraph instance

Algorithm — update_node_status()

On task success:
  Find node containing this task_id
  If all tasks in node are complete: mark node completed
  Propagate: unlock any child nodes with no other pending parents

On task failure after max_attempts:
  Mark node failed
  If failure_count < MAX_REPLAN (2):
    Decompose into child nodes (call TaskDecomposer)
    Append children to DAG, set parent to failed node
    Reset parent to "stalled" (not failed — retryable via children)
  Else:
    Mark node failed permanently
    Propagate failure signal to child nodes → mark them "blocked"

Risks

HIGH: False goal merges — two unrelated goals incorrectly joined into one DAG
Impact: Task from goal A runs in the context of goal B, confusing the Worker.
Mitigation: Conservative MATCH_THRESHOLD (0.4 keyword overlap). User can explicitly flag a new goal with a prefix like "[new]" to force creation. Log all merges to .awos/goals/merge_log.jsonl for audit.
HIGH: Stale completed nodes — re-running tasks that were already done
Impact: Repeated edits to files that were already correct, introducing regressions.
Mitigation: Verifier must re-verify completed nodes before skipping. If verifier fails on a "completed" node, reset it to "pending" and re-queue.
MEDIUM: DAG file corruption — partial write on crash
Impact: Goal graph unreadable, all history lost for that goal.
Mitigation: Atomic write pattern: write to {goal_id}.json.tmp then rename. On read, if .tmp exists, prefer the original. JSONL append-only log as backup.
MEDIUM: DAG grows unbounded over time
Impact: INDEX.json scan becomes slow; disk fills up.
Mitigation: Archive completed goals older than 30 days to .awos/goals/archive/. Cap open goals at 50. Cap nodes per goal at 200.

Open Questions — Resolved

  • Q: Should goal matching use LLM embeddings? — No for Phase 5C. Keyword overlap (Jaccard) is fast, free, and good enough for structured project descriptions. VectorMemory can be used in Phase 6+ if needed.
  • Q: Should ProjectPlanner replace Planner.plan()? — No. Planner.plan() still generates task lists. ProjectPlanner wraps the orchestration: it decides which tasks are NEW (need Planner) vs EXISTING (already in DAG).
  • Q: Multi-agent/parallel safety? — Out of scope. AWOS is single-agent. File-level locking not needed for Phase 5C.
