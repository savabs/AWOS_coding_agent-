Research: TestRunner + Test-as-Reward (Phase 5A)

doc/research phase/5 topic/self-learning topic/test-runner active 2026-05-19

Problem Statement

AWOS v4's self-learning loop (LinUCB + GPWorldModel + ReplayGate + SkillLibrary) uses syntax validation as its reward signal. A patch that compiles successfully is considered a success. This is a weak proxy — code can be syntactically valid but logically broken. The LinUCB bandit is learning to pick models that write syntactically valid code, not models that write correct code.

Upgrading to test execution as the primary reward signal means the learning loop is grounded in ground truth. Every patch that makes tests pass is a true success. Every patch that breaks tests is a true failure. This is the same approach used by SWE-RL (Meta, 2025) and the Darwin Gödel Machine (Sakana AI, 2025) — the current state of the art in self-improving coding agents.

Current Architecture

Reward Pipeline (current state)

Orchestrator.execute(task)
  → Worker.execute_task()           ← generates SEARCH/REPLACE patch
  → Verifier.verify_and_apply()     ← checks syntax only (compile/bracket check)
    → success=True  → reward computed in EscalationEngine.record_outcome()
    → success=False → SelfCorrectionEngine.suggest() → retry (max 3)
  → RewardStore.add()               ← stores Episode(success, cost, reward)
  → LinUCBRouter.update()           ← learns from that Episode

Current Reward Formula (in reward_store.py)

reward = 1.0 * success                          # 1.0 if syntax passes, else 0.0
       - η * log(cost / _MIN_COST) / log(_COST_SPREAD)  # opportunity cost penalty
       + κ * log(cost / _MIN_COST) / log(_COST_SPREAD) * (1 - success)  # failure penalty

The success boolean is set by Verifier — syntax only. This is the single point we need to upgrade.

The Gap

CURRENT:   patch applied → syntax check → success=True  → reward = +0.95
TARGET:    patch applied → syntax check → run tests → all pass → success=True  → reward = +0.95
                                                     → some fail → success=False → reward = -0.20
                                                     → test error → success=False → retry with error context

Key Research Findings

VERIFIED (SWE-RL, Meta 2025): RL with rule-based execution rewards on software engineering tasks significantly outperforms supervised fine-tuning. The reward signal used: patch similarity to oracle patch (difflib.SequenceMatcher score 0–1) + format penalty (-1 if malformed). No LLM judge needed. This confirms: objective, rule-based test outcomes are sufficient as a reward signal.
VERIFIED (Darwin Gödel Machine, Sakana AI 2025): Self-improving agent that rewrites its own code and evaluates each mutation by running benchmarks. Improved SWE-bench from 20% → 50% resolve rate. Key mechanism: run tests after every self-modification; keep only mutations that improve pass rate. This confirms: test execution as reward = ground truth for coding agents.
VERIFIED (Reflexion, Princeton 2023): After failing, agent stores verbal critique of what went wrong. On next attempt, reads prior critiques before acting. Improved HumanEval pass rates without any parameter updates. Confirms: error memory + critique injection improves retry quality. This is what our SelfCorrectionEngine does — but rule-based only, not adaptive.
VERIFIED (AFlow, ICLR 2025 Oral): MCTS over workflow topology. Smaller models outperform GPT-4o at 4.55% of inference cost by finding optimal workflow compositions. Confirms: workflow-level optimization (what we call StrategyRouter) is more powerful than prompt-level optimization alone.

Test Output Parsing — Reward Derivation

We need to extract a numeric reward from raw test output. Proposed formula:

# From pytest --tb=short -q output:
# "3 passed, 1 failed, 0 errors" → pass_rate = 3/4 = 0.75

pass_rate  = passed / (passed + failed + errors)  # 0.0–1.0
test_reward = pass_rate   # replaces the binary success bool in Episode

# When no tests exist:
test_reward = syntax_success  # fallback to current behaviour (no regression)

# When tests crash (collection error, import error):
test_reward = 0.0  # treat as failure, inject error into SelfCorrectionEngine

Integration Point

The cleanest integration is between Verifier and EscalationEngine. Verifier handles syntax. A new TestRunner module runs after a successful syntax check. EscalationEngine.record_outcome() receives test_reward instead of binary success. No other module changes needed.

Design Options

Option A — Minimal Integration (Recommended)

Add TestRunner as a new module (scaffold/agent/test_runner.py). Wire it into Orchestrator.execute() after Verifier.verify_and_apply(). The test_reward replaces success in the Episode. Zero changes to Verifier, Worker, or LinUCB interfaces. 

# scaffold/agent/test_runner.py
class TestRunner:
    def detect(self, project_root: str) → TestConfig | None
    def run(self, project_root: str, changed_files: list[str]) → TestResult

@dataclass
class TestConfig:
    runner: str        # "pytest" | "jest" | "vitest" | "make" | "go" | "cargo"
    command: list[str] # exact shell command
    timeout_sec: int   # default 60

@dataclass
class TestResult:
    passed: int
    failed: int
    errors: int
    pass_rate: float   # passed / (passed + failed + errors)
    raw_output: str    # full stdout/stderr for SelfCorrectionEngine injection
    timed_out: bool

Orchestrator change (additive only):

# After Verifier succeeds:
test_result = self.test_runner.run(project_root, changed_files)
task["test_result"] = test_result          # for SelfCorrectionEngine
self.escalation.record_outcome(
    task=task,
    reward=test_result.pass_rate,          # float, not bool
    cost=cost,
    model_name=model_name
)

Pros: additive, backward compatible, clean interface, easy to test.
Cons: full test suite runs on every patch (can be slow for large repos).

Option B — Selective Test Execution (Future Optimisation)

Run only tests related to changed files. Use pytest's --co (collect-only) to map test files to source files via import graph. Only run the subset.

Pros: 5-10× faster on large repos. Cons: complex to implement correctly; missed tests possible. Defer to Phase 6.

Option C — Parallel Test + Patch Generation

Generate N candidate patches in parallel (using parallel sub-agents), run tests on all, pick the one with highest pass_rate. This is the DGM "multi-solution ranking" strategy.

Pros: finds the best patch. Cons: N× API cost, needs parallel sub-agents (Phase 6). Defer to Phase 6.

Recommendation

Implement Option A now. Single new module, additive wiring, backward compatible. Options B and C can layer on top of Option A after Phase 5 is stable.

Risks

HIGH — Reward hacking: agent learns to write tests that trivially pass
If AWOS is also generating tests (not just production code), it could generate tests that always pass and get high reward without implementing the actual feature.
Mitigation: TestRunner only runs tests that existed BEFORE the task started (snapshot test file list at task start; ignore any new test files created during the task). New test files are accepted only if a human explicitly marks the task as "write tests".
HIGH — Circular reward: tests are incomplete, agent gets false positive reward
If the test suite has 30% coverage, 70% of bugs get reward=1.0 even when logically broken. LinUCB learns incorrect associations.
Mitigation: Pass rate (not just pass/fail) is used as reward. A project with 30% coverage will have pass_rate roughly stable. The signal is still better than syntax-only. Document this limitation clearly. Add coverage tracking as a future improvement (Phase 6).
HIGH — Test suite slowness: full suite takes 5+ minutes, blocks the pipeline
Large Django/Rails/Java projects can have test suites taking 10+ minutes.
Mitigation: Hard timeout (default 60s, configurable per project via .awos/config.json). On timeout: test_result.timed_out=True, reward falls back to syntax-only (no penalty, no reward signal). Log a warning recommending faster test subset.
MEDIUM — Flaky tests: random failures pollute the reward signal
Tests that randomly fail introduce noise into LinUCB training data. Over time this degrades routing quality.
Mitigation: Run tests twice on failure; use the better result (conservative). Track flakiness per test file in .awos/test_flakiness.json. Discount reward from known-flaky test files.
MEDIUM — Test side effects: tests mutate database, send emails, make API calls
Running tests after every patch could trigger destructive side effects on real systems.
Mitigation: AWOS only runs tests if the project has explicit test isolation markers (AWOS_SAFE_TO_RUN_TESTS=1 in env, or .awos/config.json: run_tests: true). Default is opt-in, not opt-out.
MEDIUM — No tests at all: new projects with 0 test coverage
pass_rate = undefined (0/0). Division by zero, no learning signal.
Mitigation: If no tests found or 0 tests collected, fall back to syntax-only reward. Log a notice: "No tests found. Consider adding tests to enable reward-based learning."

Open Questions (resolved before spec)

  • Q1: Do we need to sandbox test execution? — Answer: No for Phase 5A. We require opt-in (AWOS_SAFE_TO_RUN_TESTS=1). Sandboxing is a Phase 7 security item.
  • Q2: Should reward be pass_rate (float) or binary? — Answer: Float (pass_rate). SWE-RL and DGM both use continuous reward. This is richer signal for LinUCB.
  • Q3: Does the existing LinUCB handle float rewards? — Answer: Yes. LinUCBRouter.update(action_id, features, reward) accepts any float. Current reward is already a float (0.95 for cheap success, not binary 1.0).
  • Q4: Where does test error output go for SelfCorrectionEngine? — Answer: task["test_result"].raw_output gets injected as error_context in the retry prompt. SelfCorrectionEngine already handles arbitrary error_context strings.

Summary

The core idea is validated by 4 peer-reviewed papers (2023–2025) and one industry report. Test execution as reward signal is how both Meta (SWE-RL) and Sakana AI (DGM) — the two leading academic results in self-improving coding agents — ground their reward signals. AWOS is uniquely positioned to implement this at low cost (DeepSeek default model, 20-50× cheaper per iteration than GPT-4-based systems), making faster convergence of the learning loop feasible.

The key risks are reward hacking, flaky tests, and slow test suites — all addressed by the opt-in model, timeout cap, snapshot guard, and graceful fallback to syntax-only reward.
