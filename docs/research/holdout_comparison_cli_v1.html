Research: Held-out Comparison CLI v1

Date: 2026-07-30 · Status: active · Topic: operator evaluation workflow

Current architecture

  • HoldoutCorpusManifest validates holdout metadata and expected report digests.
  • compare_holdout_report_bundles verifies local artifacts and returns deterministic per-task comparison data.
  • scripts/run_evaluation_v1.py demonstrates the project’s argparse/JSON/exit-code convention.

Design requirements

RequirementDecision
Input authorityOperator supplies manifest, baseline artifact, and candidate artifact paths explicitly; the CLI never resolves or fetches external URIs.
OutputStable sorted JSON to stdout, with optional exact file output.
Exit code0 only when evidence verifies and no correctness/safety regression exists; non-zero for every other result.
PrivacyDo not print report contents, task requests, or private paths beyond user-supplied error context.

Verified guidance

  • SWE-bench documents command-line evaluation, per-instance results, and non-zero operational failures as part of reproducible benchmark execution.
  • OpenHands evaluation workflows preserve metadata, metrics, history, errors, and output artifacts for each instance.
  • OpenAI evaluation guidance recommends automated repeatable comparisons, detailed logs, held-out data, and explicit metrics rather than vibe-based judgments.

Risks

False green: a CLI could return zero after a regression. Mitigation: exit zero only when comparison.regressed is false.

Accidental exposure: printing full reports could leak private task data. Mitigation: print only comparison metadata and paths/errors supplied by the operator.

Silent output loss: a report file may not be persisted. Mitigation: write atomically through a temporary sibling and replace only after comparison succeeds.
