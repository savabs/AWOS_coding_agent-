2. Claude Code Source Analysis (src/)

This is the most valuable source. Claude Code is the #1 coding agent by usage. Reading its actual production TypeScript source reveals exactly how they solve every problem AWOS struggles with.

2.1 The Edit Format — JSON Structured Tool, NOT Text Blocks

🚨 Critical Finding: Claude Code does NOT use <<<SEARCH/>>>REPLACE text blocks. It uses a structured JSON tool call with old_string and new_string fields. The LLM emits structured JSON; a validator processes it before any disk write.

From src/tools/FileEditTool/FileEditTool.ts, the tool schema is:

{ file_path: string, // absolute path old_string: string, // exact text to replace (empty = create file) new_string: string, // replacement text replace_all?: boolean // default false }

The validateInput() method enforces these rules in order:

  1. Must read first: readFileState.get(fullFilePath) must exist — error if not read this session
  2. File modification guard: compare lastWriteTime vs readTimestamp — if file changed since read, reject with "Read it again"
  3. Quote normalization: findActualString() normalizes curly quotes ↔ straight quotes before search
  4. Not found: If old_string not in file → error "String to replace not found in file."
  5. Multiple match detection: Count occurrences — if >1 and replace_all=false → error with count and instruction to add more context
  6. No-op detection: old_string === new_string → reject immediately
  7. Security: Check for secrets in new_string before writing to team memory files

The apply logic in utils.ts:

function applyEditToFile(originalContent, oldString, newString, replaceAll = false) { // Trailing newline stripping: if old_string doesn't end with \n // but file has old_string + \n, strip the trailing newline too const stripTrailingNewline = !oldString.endsWith('\n') && originalContent.includes(oldString + '\n') return stripTrailingNewline ? content.replace(oldString + '\n', newString) : content.replace(oldString, newString) }

2.4 Skills System

From skills/loadSkillsDir.ts — skills are Markdown files with YAML frontmatter discovered from .claude/skills/ directories:

Skills are discovered at runtime, matched by keyword relevance to the current task, and injected as context. They're persistent across sessions — equivalent to few-shot examples that survive restarts.

2.5 LSP Diagnostic Registry

From services/lsp/LSPDiagnosticRegistry.ts:

  • Live LSP server (pyright/pylsp) processes every file write asynchronously
  • publishDiagnostics notifications are registered in a global registry
  • Next LLM turn automatically receives diagnostics as attachments (max 10/file, 30 total)
  • LRU deduplication prevents the same diagnostic appearing across turns
  • Result: LLM sees type errors, undefined references, syntax errors without running anything

3. Aider Edit Format Research

Aider is the SOTA open-source coding assistant. It has extensively researched edit formats and their reliability across models.

3.1 The 5 Edit Formats

FormatSyntaxBest ForKey Weakness
wholeReturn entire file in fenced blockSmall files, simple changesExpensive — full file regeneration
diff<<<SEARCH / ======= / >>>REPLACEMost models (default)Whitespace/indentation sensitivity
diff-fencedSame but file path inside fenceGemini familySame as diff

editor-diffArchitect plain text → Editor diffHigh-quality editsTwo model calls per task

3.2 Architect Mode (The Gold Standard)

Aider's architect mode separates reasoning from editing. The architect model describes what to change in plain text. The editor model converts those instructions into syntactically correct edits. This produces significantly higher quality edits because each model does only what it's good at.

Quote from Aider docs: "The architect model resolves the coding task and provides plain text instructions about which file changes need to be made. The editor interprets those instructions to produce the syntactically correct diff or whole edits."

3.3 Why SEARCH/REPLACE Fails

From research: The 4 root causes of SEARCH block mismatches:

  1. Whitespace drift: LLM omits trailing spaces, changes indentation
  2. Context drift: LLM reconstructs from memory, not exact file content
  3. Curly quote substitution: LLM emits typographic quotes, file has ASCII
  4. Partial view problem: LLM writes SEARCH based on a snippet, not full file

All 4 are solved by switching to JSON structured tool calls + read-before-write enforcement.

4. OpenHands Architecture

OpenHands (formerly OpenDevin) is the leading open-source coding agent platform with 64k+ GitHub stars.

4.2 CodeAct Pattern — Code as Universal Action

OpenHands' key innovation: the agent writes Python code as its primary action (not tool calls). This makes every action testable, observable, and replayable. Bash execution, file edits, web browsing — all done through Python code execution in a sandboxed Jupyter kernel.

4.3 Delegation Pattern

Complex tasks are delegated to specialized sub-agents: a main CodeAct agent can spawn a Browser Agent for web tasks, or a specialized test-writing agent. The delegation is explicit in the event stream.

5. SWE-Agent ACI

SWE-Agent from Princeton introduces the Agent-Computer Interface (ACI) concept — a deliberately simplified tool set designed to maximize LLM coding performance.

5.1 The ACI Design Philosophy

┌─────────────────────────────────────┐ │ SWE-Agent ACI │ │ Simplified Actions: │ │ - view_file(path, start, end) │ │ - search_dir(pattern, dir) │ │ - edit_file(path, changes) │ │ - run_command(cmd) │ │ │ │ Guardrails: │ │ - Syntax checking after each edit │ │ - Linting │ │ - Test execution │ │ │ │ Context Window: │ │ - Last 5 steps only (condensed) │ └─────────────────────────────────────┘

5.2 Condensed History (Critical Cost Optimization)

SWE-Agent keeps only the last 5 steps condensed in the context window — not the full history. This keeps costs low and forces the model to reason from current state rather than distant history. AWOS sends the full task description + all context on every retry.

6.2 What's Driving the Improvements

From academic analysis (SWE-EVO, MASAI, Agentless papers):

  1. Test execution as oracle: All top agents use test pass/fail as ground truth. Not LLM self-evaluation.
  2. Parallel sampling + selection: Generate N patches, pick best by test execution (like Agentless)
  3. Localization first: File-level then symbol-level localization before attempting any edit
  4. Worktree isolation: Each attempt in its own git worktree — safe parallelism
  5. Structured edits: JSON tool schema, not text block parsing
  6. Better scaffolding beats better model: Scaffolding improvements matter more than model upgrades at equal capability

6.3 Artificial Analysis Benchmark Task Types

The composite index measures three dimensions:

  • SWE-Bench-Pro-Hard: Make a working patch (code changes + test pass) — needs multi-file reasoning + test execution
  • Terminal-Bench v2: Shell workflow navigation — needs bash execution
  • SWE-Atlas-QnA: Repository understanding — needs good code reading/search
AWOS is strong at QnA-style but fails on patch-that-works style. The gap: test execution as verification.

7. Prompt Caching Economics

7.1 What's Available

Anthropic90%85%5 min (ephemeral)

7.2 How Claude Code Uses It

Claude Code's compact prompt design is architected around cache stability:

  • System instructions = one stable cache_control: ephemeral block (changes rarely)
  • User messages = always appended (never mutate system block)
  • Per ProjectDiscovery case study: 59% total cost reduction achieved this way

7.3 AWOS Current Problem

AWOS's Planner creates a new Anthropic client on every execute_feature call. Each call re-sends the full system prompt as uncached tokens. With Sonnet at $3/MTok and ~2k-token system prompts, this wastes ~$0.006 per plan call that could be ~$0.0006 with caching.

Fix: Keep a module-level client singleton. The system prompt block never changes between calls in the same process — it will cache after the first call.

8.2 Integration Pattern from Claude Code

Pattern (from src/services/lsp/LSPDiagnosticRegistry.ts): 1. Start pyright/pylsp server as subprocess 2. Every file write → LSP processes it (textDocument/didChange) 3. LSP sends publishDiagnostics notification async 4. Registry stores diagnostics: max 10/file, 30 total 5. LRU dedup: same diagnostic not repeated across turns 6. Next LLM turn: diagnostics injected as system attachment 7. LLM sees errors immediately without running anything

8.3 Python LSP Options

  • pyright: Best type checking, Microsoft, fast (Node.js)
  • pylsp: Pure Python, slower, more widely compatible
  • ruff: Fast linting (Rust), not full LSP but excellent diagnostics
  • tree-sitter fallback: When no LSP available, structural analysis

For AWOS: ruff as quick win (fast, Python, no server overhead), pyright for full LSP.
