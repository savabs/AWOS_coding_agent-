Research: Held-out Evaluation Corpus v1

Date: 2026-07-30 · Status: active · Topic: evaluation integrity

Objective

Make it possible to evaluate AWOS against tasks that were not used for prompt, reward, or implementation tuning, without placing private task contents in the public repository.

Current system

ComponentCurrent behaviorGap
EvaluationFixtureValidates task metadata, argv acceptance checks, paths, and schema version.No corpus-level split, hash, environment, or baseline identity.
EvaluationReportAggregates trial outcomes and compares baseline/candidate reports for one task.No manifest tying many task reports to an immutable corpus and environment.
Public fixturesFour families under tests/fixtures/evaluation_v1/.Useful for harness contracts, not an unbiased capability estimate.

Verified external guidance

  • SWE-bench evaluation guide: apply patches to isolated repository environments and run tests; report per-instance and aggregate outcomes.
  • OpenHands evaluation harness: use per-instance metadata, isolated runtimes, reproducible configuration, histories, metrics, and errors.
  • OpenAI evaluation best practices: use task-specific datasets, held-out sets, continuous comparison, logging, automation, and human calibration; avoid biased or vibe-based metrics.
  • OpenHands benchmarks: benchmark repositories separate benchmark definitions, reproducible environment/version metadata, and detailed run outputs.

Design observations

  • A holdout manifest must identify the split as holdout; otherwise a public fixture can be mislabeled accidentally.
  • Hashes must cover the fixture inputs and repository snapshot, not only a task ID.
  • Environment identity must be explicit because package/model/runtime drift can change results.
  • Baseline and candidate reports need immutable paths or content digests; a mutable “latest” pointer is insufficient evidence.
  • Private fixture contents should remain outside this repository; only a contract/example manifest belongs here.

Risks

Leakage: public fixture paths or IDs can enter a holdout manifest. Mitigation: reject paths below tests/fixtures/evaluation_v1 and require a holdout split.

Mutable evidence: reports can be overwritten after comparison. Mitigation: require report SHA-256 digests and immutable artifact references.

False precision: a small holdout set can produce unstable estimates. Mitigation: report task count, per-family results, and avoid presenting a single score as production capability.
