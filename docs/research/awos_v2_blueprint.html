v2 Blueprint: Executive Summary

The AWOS v2 Blueprint extends the current AWOS MVP (Phases 0–3) with five new foundational layers that maximize "Intelligence Density" by treating code as a structural XML tree rather than flat text.

Five-Layer Architecture

  1. Layer 1: Universal Cartographer — Tree-Sitter-based AST indexing + STRUCT.xml output with incremental sync via content hashing (XXH3)
  2. Layer 2: Adaptive Dispatcher — Complexity scoring + provider-agnostic model routing (Tier 1–4)
  3. Layer 3: Transparency & HITL — Pre-flight manifest + consent gate (default: Deny)
  4. Layer 4: Hydration Protocol — Smart prefix selection + prompt caching (10% read cost reduction)
  5. Layer 5: Project Soul — SOUL.xml persistence: rules, decisions, learned patterns, cost history
Integration Strategy: Extend MVP (Phases 0–3), not replace. v2 builds on the CLI scaffolding and model tiering already implemented. Layers 1–5 layer atop Phase 0, progressively unblocking Phases 2–3 functionality.

Why This Approach Works

  • Structural Awareness: Parse once, route intelligently. STRUCT.xml is the "north star" — agent doesn't navigate flat code.
  • Token Efficiency: Hydration protocol eliminates context bloat. Fetch only needed symbols; wrap in <active_code> tags.
  • Measurable Cost Reduction: Prompt caching alone = 90% reduction on repeated contexts. Multi-provider routing = 21× cheaper on commodity tasks.
  • Memory & Continuity: SOUL.xml learns from every session. Prevents repeated mistakes; compounds good decisions.
  • User Authority: HITL consent gate ensures human oversight. Default-deny prevents runaway spend.

Layer 1: Universal Cartographer — Tree-Sitter Deep Dive

What is Tree-Sitter?

Tree-Sitter is a parser generator that builds Abstract Syntax Trees (AST) for code. Key properties:

  • Language-agnostic: 30+ official parsers (C, C++, Python, Rust, JavaScript, Go, etc.); 40+ community parsers
  • Incremental parsing: Updates only modified branches; no re-parse of entire file
  • Error recovery: Returns useful AST even with syntax errors
  • Lightweight: Pure C core; bindings for Python (py-tree-sitter official), Rust, JS, Go, etc.
  • Production-proven: Used by GitHub Copilot, VS Code, Neovim
VERIFIED: Tree-Sitter supports all major languages required by MVP scope. Official Python bindings via tree-sitter package. Incremental sync enables file-watcher architecture.

STRUCT.xml Output Format

The Cartographer generates a hierarchical XML map of the repository:

<repository>
  <folder name="src">
    <file path="main.py" hash="abc123def456">
      <symbol id="f1" type="function" name="render" signature="def render()" line="42"/>
      <symbol id="c1" type="class" name="Renderer" line="10"/>
    </file>
  </folder>
</repository>
Element Content Purpose
folder Directory structure Organize symbols by file location
file path, hash (XXH3) Track file identity; hash detects changes
symbol id, type, name, signature, line Addressable code artifacts for hydration

Incremental Sync via Content Hashing

File watchers (Watchdog library) trigger re-parse on file changes. XXH3 hash comparison prevents redundant parsing:

  • Hash matches: No change, skip re-parse
  • Hash differs: Re-parse only that file, update STRUCT.xml branches
  • New file: Parse + add to STRUCT.xml tree
  • Deleted file: Remove from tree
VERIFIED: xxhash3-64 available via PyPI. Content hashing is production-standard for cache invalidation.

Layer 4: Hydration Protocol — Prompt Caching Strategy

Why Prompt Caching Matters

Traditional LLM workflows send the full context on every request. Prompt caching allows the model to reuse previously processed token prefixes at 10% of the input cost.

Scenario Without Caching With Caching Savings
System prompt + 50KB codebase (first call) $0.50 (full input) $0.50 (cache write @ 1.25×) None (baseline)
Second call (same prefix) $0.50 (full input) $0.05 (cache read @ 0.1×) 90%
100 repeated hydration cycles $50.00 $5.50 (1 write + 99 reads) 89%
VERIFIED: Anthropic Claude Sonnet-4.6+, Claude Opus-4.5+ support automatic cache management. Cache read cost = 10% of input token price. Cache write cost = 25% (5-min TTL) or 200% (1-hr TTL).

Hydration Protocol: Observe → Select → Hydrate

The workflow minimizes input tokens by reading only required code:

  1. Observe: Agent reads STRUCT.xml (the skeleton, ~5KB uncompressed)
  2. Select: Identify symbols to modify (e.g., <symbol id="f42">)
  3. Hydrate: Fetch only that symbol's source block from disk + wrap in <active_code> tags
  4. Prompt Cache: STRUCT.xml + system instructions cached; only task-specific message is fresh
Request 1 (cache write):
  - STRUCT.xml (5KB)
  - System instructions (2KB)
  - Task: "Fix function f42"
  - Hydrated code for f42 (200 bytes)
  RESULT: 7KB written to cache

Request 2 (cache read, different task):
  - STRUCT.xml (READ FROM CACHE)
  - System instructions (READ FROM CACHE)
  - Task: "Add tests for f42"
  - Hydrated code for f42 (200 bytes)
  RESULT: 7KB read @ 10% cost; only 200 bytes fresh input
Insight: For projects with N files and M average tasks per file, caching the STRUCT.xml alone saves ~89% on input tokens after the first task. Multi-task sessions are the primary beneficiary.

Model Input $/MTok Cache Read $/MTok Min Cache Size TTL Options

Layer 2: Adaptive Dispatcher — Multi-Provider Model Routing

Why Multi-Provider Routing?

Different tasks require different models. Routing by task complexity ensures:

  • Cost efficiency: 70% cheaper tasks don't need Opus
  • Speed: Nano/Flash models respond faster for simple tasks
  • Resilience: If one provider is rate-limited, failover to another
  • Flexibility: Swap models without rewriting prompts

Five-Tier Model Hierarchy

Tier Model(s) Task Type Cost Ratio Polyglot Score
1 (Architect) Claude Opus-4.7 / GPT-5* Architecture, heavy logic, planning 1.0× 70.7%
2 (Pro) Claude Sonnet-4.6 Feature development, refactoring 0.6× 56.4%
3 (Rapid) DeepSeek-V4 / Qwen 2.5 Boilerplate, unit tests, typing 0.05× 70.2%
4 (Nano) Gemini-3.1 Flash / GPT-4 Mini Complexity scoring, summarization 0.02× 44%
KEY INSIGHT (verified 2026-05-13): DeepSeek-Chat costs $0.14/MTok (input) vs Claude Sonnet at $3.00/MTok — a 21× difference — with 70.2% polyglot score vs Sonnet's 56.4%. DeepSeek is the default for commodity tasks.

Routing Algorithm

  1. Complexity Scoring: A Tier 4 model scans the task description (free/cheap). Returns score 1–10.
  2. Routing Decision:
    • Score 1–4 → Tier 3 (DeepSeek-Chat, ~$0.01 per task)
    • Score 5–7 → Tier 2 (Claude Sonnet, ~$0.10 per task)
    • Score 8–10 → Tier 1 (Claude Opus, ~$0.50 per task)
  3. Escalation Rule: If Tier 2/3 fails build twice, propose escalation to Tier 1 with "Reasoning Review" context.
  4. Provider Failover: If API rate-limited, retry with secondary provider.

Decision: Default Provider = DeepSeek

DeepSeek-Chat (deepseek/deepseek-chat via LiteLLM) is now the primary router choice for:

  • Commodity coding tasks (tests, boilerplate, type annotations)
  • Tasks scoring 1–5 on complexity scale
  • First-pass attempts before escalation

Rationale: 21× lower cost than Claude Sonnet, equivalent polyglot performance, proven via Aider benchmark.

User Authority: Human makes the final call. No surprises. No hidden spend.

The Consent Gate

User response options:

Key Action Result
[A] Approve Execute with suggested model/cost
[S] Switch Model/Provider Show alternatives; user selects from dropdown
[O] Omni-Mode User pre-approves all tasks for this session
[D] Deny Cancel task; explain why it was proposed
DEFAULT MODE (per user decision): [D]eny by default — Block every call; user must approve each task. Prevents accidental spend.

Layer 5: Project Soul — Persistent Architectural Consciousness

What is SOUL.xml?

A persistent XML file (`.awos/soul.xml`) that remembers the "why" of the codebase across sessions:

<soul>
  <project name="my_service" created="2026-01-15">
    <invariants>
      <rule id="r1">Zero-copy only for buffers > 1MB</rule>
      <rule id="r2">No dynamic allocation in hot path</rule>
      <rule id="r3">Python 3.9+ only; no 2.7 support</rule>
    </invariants>
    <patterns>
      <pattern id="p1" issue="Segfault on realloc" 
               fix="Use arena allocator" frequency="3"/>
      <pattern id="p2" issue="Type confusion in protobuf" 
               fix="Always validate msgtype before cast" frequency="2"/>
    </patterns>
    <decisions>
      <decision id="d1" date="2026-02-20" 
                 choice="Chose Vulkan over DX12">
        Reason: Cross-platform, lower API overhead, better tool ecosystem.
      </decision>
    </decisions>
    <cost_history>
      <month date="2026-05">
        <metric key="avg_model_tier">2.3</metric>
        <metric key="cache_hit_rate">0.78</metric>
        <metric key="total_spend">$142.55</metric>
      </month>
    </cost_history>
  </project>
</soul>

The "Dreaming" Cycle

After each session ends, a Tier 4 model summarizes activity and updates SOUL.xml:

  1. Extract new rules from code changes
  2. Detect repeated bugs; add to patterns
  3. Log architectural choices
  4. Record cost metrics
Session end → extract_session_summary() 
                      → prompt Tier 4 model 
                      → parse rules/patterns/decisions 
                      → merge into SOUL.xml 
                      → checkpoint session

Next session → read SOUL.xml 
             → agent already knows project history 
             → prevents repeated mistakes
Benefit: Agent "wakes up" each session with full project context. No context switching cost.

SOUL.xml Content (per user decision)

Section Content Update Frequency Use Cases
invariants Hard project rules (no exceptions) Rarely (~quarterly) Enforce architecture, prevent regressions
patterns Bug signatures + fixes (learned) Every session Auto-detect similar bugs; suggest fixes
decisions Architecture choices + rationale When decision is made Context for future trade-offs
cost_history Monthly metrics (spend, cache hit %, model tiers used) Monthly rollup Budget forecasting, trend analysis

Key Decisions Made for v2 Blueprint

Decision 1: Integration Strategy
Choice: Extend the MVP (Phases 0–3), not replace.
Rationale: Current Phase 0 CLI + model tiering are solid. v2 builds on this foundation, layering Cartographer, Dispatcher, Hydration, and Soul as add-ons.
Decision 2: Language Scope
Choice: Support all major languages (Python, C/C++, Rust, Go, JavaScript, Java) from day 1.
Rationale: Tree-Sitter's polyglot support makes this cheap. MVP focus is Python + C/C++; others extend naturally via grammar plugins.
Decision 3: HITL Consent Default
Choice: Deny by default — block every API call; user must explicitly approve.
Rationale: Prevents surprise spending. Reduces friction: user approves Omni-Mode once per session if desired.
Decision 4: Primary Provider
Choice: DeepSeek-Chat as default for Tier 3 + Tier 4 tasks.
Rationale: 21× cheaper than Claude Sonnet, equivalent polyglot performance (70.2% vs 56.4%). Proven in Aider benchmark. Tier 1 tasks still use Claude Opus for reasoning.
Decision 5: SOUL.xml Scope
Choice: Persist rules, decisions, learned bug patterns, and cost history.
Rationale: Maximizes agent learning. Cost history enables forecasting and budget alerts. Patterns prevent repeated mistakes.
Decision 6: Prompt Caching Strategy
Choice: Cache STRUCT.xml + system instructions; hydrate only task-specific symbols.
Rationale: 89% input token reduction after first task. Multi-task sessions benefit most. 5-minute cache TTL is sufficient for typical development loops.
