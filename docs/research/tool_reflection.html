Research: Tool Reflection / Success Matrix

doc/research phase/8 topic/tool-reflection active 2026-05-20

Current Architecture

The AWOS orchestrator already has a ToolPerformanceTracker that is initialized and partially wired. The success matrix data structure exists but is never displayed and never influences routing. This feature completes the loop.

Data Flow (current — incomplete)

  1. Worker attempt completes → _execute_single_task calls performance.record(tool="Worker", model=..., task_type=complexity, success=...)
  2. Records accumulate in .awos/performance.json silently
  3. success_matrix() is never called. recommend_model() is never called. Data is dead weight.

Data Flow (after this feature)

  1. Worker completes → performance.record() with enriched latency_ms, cost_usd, semantic task_type
  2. execute_feature prints success matrix panel (Phase 5) after each run
  3. EscalationEngine.decide() calls performance.recommend_model() as a soft hint; if the recommended model matches a tier, preference it (min 5 samples required — cold-start safe)

Observations

Key Findings

  • performance.record() IS partially wired — orchestrator.py lines 766 and 781 call it, but only pass tool="Worker", model=..., task_type=task.get("complexity"), success=bool. Missing: latency_ms and cost.
  • success_matrix() is never called — confirmed by grep. The method is fully implemented in performance_tracker.py:94–138 and returns a useful {model → {task_type → {count, success_rate, avg_latency_ms, avg_cost, top_error}}} dict. But nothing reads it.
  • recommend_model() is never called — confirmed by grep. Method exists at line 165 of performance_tracker.py. EscalationEngine never uses it.
  • Latency data is available — _span.worker_start_ts is set in _execute_single_task; computing latency_ms = (time.time() - _span.worker_start_ts) * 1000 at the record() call site is trivial.
  • Cost data is available — esc_decision.spec.cost_per_req is already used in reward_store.store() at the same code path.
  • Semantic task_type can be derived cheaply — ml_router.py already has keyword sets (_BUG_FIX_KW, _REFACTOR_KW, _NEW_FEAT_KW, _ARCH_KW, _TEST_KW). A 5-line helper classifies task["action"] → one of: bug_fix | refactor | new_feature | architecture | test | general.
  • Display pattern is established — Phases 1–4 in execute_feature print panels via .display() methods. Success matrix panel slots in as Phase 5 in the same section (lines 371–398).
  • EscalationEngine already accepts ml_router as a soft hint — the pattern of "soft hint that fires after hard overrides but before heuristics" exists in escalation_engine.py for LinUCBRouter. The same pattern can be used for performance.recommend_model().
  • No tests exist for ToolPerformanceTracker — confirmed by: no test_performance_tracker.py found in tests/. The class itself is well-written and testable.

Algorithm Survey

No new math required. success_matrix() is pure frequency statistics: success_rate = successes / count, avg_latency = mean(latencies). The best_model_for() method uses argmax(success_rate) over candidates — correct and simple. Cold-start protection (min_count=5) prevents routing decisions from n=1 noisy data.

Data Requirements

  • Storage: .awos/performance.json (already exists, append-only pattern same as other stores)
  • Schema: existing record schema is sufficient once latency_ms and cost_usd are populated
  • Volume: at 5–50 tasks/day, the window=100 default is appropriate; no compaction needed
  • Cold start: matrix is empty on first run; display panel is no-op if count < min_count (3 by default)

Risks

HIGH: Soft routing hint could conflict with LinUCBRouter
Both performance.recommend_model() and LinUCBRouter are soft hints in EscalationEngine. If they disagree, the last one applied wins (whichever is later in the decide() flow). This could produce unexpected behavior.
Mitigation: Apply performance hint ONLY as a tie-breaker when LinUCB has no opinion (cold-start, <20 episodes). This makes them non-conflicting by construction. Document the precedence order explicitly.
MEDIUM: performance.json file format mismatch
The existing _load() reads the whole file as a JSON array. But _append_to_disk() appends newline-delimited JSON objects (JSONL). This means after the first session the file is neither valid JSON nor valid JSONL.
Mitigation: This is a pre-existing bug in performance_tracker.py. Fix it as part of this feature: switch _append_to_disk to JSONL (one record per line) and _load to read JSONL lines. Add a migration step for existing files. Covered in spec Step 1.
MEDIUM: latency_ms is wall clock, not pure worker latency
_span.worker_start_ts includes all retries and the verifier. Single-attempt latency is not separately tracked.
Mitigation: Document this as "task latency" not "model latency". Still useful as a routing signal. No action needed for v1.

Open Questions

  • Should the performance hint hard-override a model, or only influence the escalation level? — Answer: influence only. Hard override risks ignoring budget constraints. Soft hint is sufficient.
  • Should the success matrix display be skipped if fewer than N total records exist? — Answer: yes, skip if total records < 3 (same as success_matrix min_count default). Keeps the panel clean for fresh installs.
