Expected Data Flow

  1. Advanced Planner returns a graph.
  2. Orchestrator validates and restores it as an ExecutionGraph.
  3. Each graph node is dispatched according to its type.
  4. Independent nodes run in the same safe wave; dependencies wait.
  5. Tests, barriers, reviews, and final verification remain visible nodes rather than being disguised as edits.
  6. Each wave is persisted to RuntimeSession.execution_graph>.
  7. GoalGraph progress is updated from stable node IDs.

Observations

  • The advanced Planner is the project decomposition authority; CheapPlanner remains a fallback/task-level planner.
  • Legacy execution must remain unchanged when the response has only plan or when CheapPlanner is used.
  • Native
    • graph execution should be gated by the presence of a validated execution_graph, not by model name.>
  • The existing graph executor does not
    • invent recovery nodes. Recovery insertion remains explicit and must be handled by the orchestration policy.
  • Existing runtime progress uses task IDs, so native node IDs need a stable mapping or a graph-specific progress update.
  • Full repository lint is not
    • a reliable gate because the repository has many pre-existing Obsidian errors; focused tests are required.
2>Risks and Mitigations
High: Executing a malformed or semantically vague graph could edit the wrong files. Mitigation: validate the Planner contract again at the runtime boundary and fail closed.
High: Treating tests/barriers as ordinary edits could skip verification. Mitigation: type-specific dispatch with explicit read-only/test behavior.
Medium: Native and legacy progress identifiers may diverge. Mitigation: define stable node-to-task metadata and test pause/resume.
Medium: Existing retry/replan loops may duplicate native recovery behavior. Mitigation: keep native graph execution behind an explicit path and do not run legacy task replan logic against graph-only nodes.

Non-goals

  • Changing the advanced Planner contract.
  • Changing CheapPlanner's responsibility or model tier.
  • Adding a dependency or provider.
  • Replacing the existing Worker, Verifier, TestRunner, or GoalGraph.
  • Building the 10–20-file evaluation in this task; that
    • follows after the runtime path is proven.>
