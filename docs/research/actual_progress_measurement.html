Research: Measuring Actual Progress in an AI-Built Project

Phase: N (foundational) · Date: 2026-07-06 · Tags: topic/progress topic/measurement topic/quality-gate

1. The Problem

This project (AWOS) has ~40K LOC across 140+ modules, 1035 collected tests, 60+ task files, 57 checkpoints, 16 live proof demos — and yet it feels like we're circling.

The root cause is not lack of work. The root cause is that the progress measurement system is untrustworthy. An LLM agent marks task steps [x] with no external verification. The human reads the task file, sees 9/10 steps done, and thinks "great, 90% progress." But the remaining step may be the hardest one, or the 9 done steps may not actually integrate into working software.

Current belief: "Task X is 13/14 steps done → 93% complete"

Undiscovered truth: The 13 steps produced code that passes unit tests but breaks in integration. The 1 remaining step is "test on external repo" — the hardest part. Actual progress: ~30%

3. The Core Gap

The Earned Value Problem for AI Work

In project management terms:

  • Planned Value (PV): Steps marked [x] in task files
  • Earned Value (EV): Features that actually work end-to-end
  • Actual Cost (AC): LLM calls, human time, compute spent

Our current system assumes PV = EV. It assumes that if the LLM marked a step [x], the value was actually earned. This is false.

The LLM agent has incentives to mark things done (to complete its session, to show progress). There is no independent verification step between "I wrote the code" and "the feature works."

Specific gaps found:

  1. No integration test requirement. Unit tests pass, but no test validates the full pipeline (planner → worker → verifier → reward). The 24 failing tests are in routing and verification — core kernel claims.
  2. No abandonment detection. 15+ task files with 0 done steps exist silently. No mechanism flags them as abandoned.
  3. No demo regression check. 16 demos exist, but nothing ensures they still work after code changes.
  4. Checkpoints are templates, not records. The July 5 checkpoint has "TODO" in every substantive section.
  5. Task files are accumulated, not curated. 60+ active tasks, most with low or zero progress, creates the illusion of scope without delivery.
  6. Collecting errors in test suite. 31 fixture tests fail at collection time with broken relative imports — and nobody fixes them because they're "fixtures."

4. External Patterns Researched

4.1 Definition of Done (Scrum/Agile)

Core idea: Before any work item is marked "done," it must pass a predefined checklist. Common items: code reviewed, unit tested, integration tested, documented, deployed to staging.

Applicable insight: An AI project needs a Definition of Done that includes independent verification — not just "the LLM wrote code and unit tests pass."

4.2 Earned Value Management (EVM)

Core idea: Track three curves — Planned Value (what you said you'd do by now), Earned Value (what you actually accomplished), Actual Cost (what it cost). The gap between PV and EV is the true variance.

Applicable insight: For AI work, the earned value is not "code written" but "working, integrated feature." Measuring this requires an objective gate — an integration test or a live proof run — before value is "earned."

4.3 Acceptance Test-Driven Development (ATDD)

Core idea: Write the acceptance test before writing the feature. The feature is only done when the test passes.

Applicable insight: The most honest progress metric is: "How many acceptance-level tests pass?" Not "how many task steps are marked [x]."

4.4 Test Coverage as Progress (CI/CD Pipeline)

Core idea: In CI/CD, the deploy gate is: all tests pass, coverage >= threshold, lint clean. Nothing is "done" until it passes the pipeline.

Applicable insight: Our quality_gate.py almost does this, but it checks task-file formatting, not actual pipeline pass/fail.

5. Proposed Mechanism: Verified Progress Snapshot (VPS)

Based on the research, here is a proposed mechanism that would give honest progress measurement. This is a spec sketch — not implementation.

Core Principle

A task step is NOT done until an independent, automated verification confirms it. The LLM can mark [~] (in progress). Only the verification system can promote it to [x].

Five components:

1. Feature → Test Mapping (mandatory)

Every task spec must include a TestEvidence section that names the specific test file(s) that prove the feature works. The system then verifies:

  • Those test files exist
  • They pass on current code
  • They cover the feature (not just unrelated tests)

2. Integration Pipeline as Progress Gate

A single command python scripts/progress_snapshot.py produces an honest JSON report:

{ "features": [ {"name": "self-improving coding agent", "status": "in_progress", "tests_passing": 20, "tests_total": 30, "demo_last_run": "2026-06-25", "integration_test_pass": false, "working_e2e": false} ], "test_suite": {"pass": 988, "fail": 24, "collect_errors": 31}, "abandoned_tasks": ["ml_meta_controller_task", "vector_memory_task", ...], "stale_demos": ["demo_ci_rescue.sh", "demo_clawcode.sh", ...], "checkpoint_quality": {"july_5_checkpoint": "TODO_TEMPLATE"} }

3. Abandonment Detection

Any task file with 0 progress for >7 days is automatically flagged. After 30 days, it's archived to tasks/zombie/.

4. Demo Regression Harness

Each demo script in scripts/demo_*.sh is run weekly (or on-demand) and its output compared to stored "golden" output. A demo that no longer produces correct output = regression detected.

5. Honest Burndown (EV not PV)

Display two curves on the dashboard:

  • Blue: Planned tasks (task steps marked [x] by LLM) — what was attempted
  • Green: Verified features (features where integration test passes + demo runs) — what actually works

The gap between blue and green is the "LLM hallucination gap" — the honest measure of how much of our work is real.

6. What Next?

This research doc is not a spec — it's the understanding phase. The natural next steps would be:

  1. Decide which components of the VPS mechanism to implement first
  2. Write a spec with atomic implementation steps
  3. Build the progress_snapshot.py tool as the first deliverable (it's a read-only analysis — low risk)
  4. Then build the abandonment detector, then the demo regression harness

But before any implementation: do you agree with the diagnosis? Does the proposed mechanism address the "circling" feeling?
