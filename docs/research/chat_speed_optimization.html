Root Causes Found

1. BUG: max_tokens forced to 2048

gui_chat.py line 1045: max_tokens = 2048 — hardcoded override ignores the parameter passed by caller.

Impact: Every query can generate up to 2048 output tokens. A simple "What is Python?" generates 200+ tokens unnecessarily. With 256 cap it'd be ~7s; with 2048 it's ~16s. The model generates longer responses with the larger cap.

2. Context overhead: 12K chars of project docs on every query

_read_project_context() always loads VISION.md (2K), project_structure.md (2K), README (2K), plus SymbolIndex-matched files (2-6K). This is 3K+ input tokens that add ~1.5s to TTFB. For "What is Python?" queries, this context is irrelevant.

3. Duplicate context loading

_build_qa_prompt() calls _read_project_context(). Then _stream_qa() also calls _qa_context_blob() which calls _read_project_context() again. Same context loaded twice per query.

4. Artificial time.sleep delays

LocationDelayPurpose
gui_chat:529 (cache path)8ms/chunkSimulated typing for cache hits
gui_chat:402 (plan path)12ms/chunkSimulated typing for plan display

Cache hit: ~25 chunks × 8ms = 200ms artificial delay. Plan: ~40 chunks × 12ms = 480ms.

5. 20s total timeout in fallback chain

_stream_opencode_go has 6s per-model timeout and 20s total. If MiniMax M3 goes down, the chain tries 8 more models × 6s = up to 20s before failing.

Fix Strategy (ordered by impact/cost ratio)

  1. Remove max_tokens override — 1-line fix, restores caller control. Add dynamic sizing based on query complexity.
  2. Short-circuit context for non-codebase queries — Skip SymbolIndex and project docs for generic questions.
  3. Eliminate duplicate context loading — Load once per query in _stream_qa, pass to both _build_qa_prompt and _qa_context_blob.
  4. Reduce/remove artificial delays — Use 2ms instead of 8ms for cache, remove for plan path.
  5. Reduce fallback timeout — 4s per model, 12s total (from 6s/20s).
