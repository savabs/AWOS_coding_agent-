Research: Self-Learning Reward Evaluation v1

phase/2 · topic/evaluation · active · 2026-07-29

Question

How can AWOS determine whether a coding-agent improvement is real, replayable, safer, and cheaper rather than merely producing a better-looking reward number?

Decision: correctness is a hard gate. Reward is a separate diagnostic signal for efficiency and learning. A run that fails hidden acceptance tests cannot be successful regardless of cost, speed, or model confidence.

Proposed evaluation model

1. Task fixture

Each fixture has a public task request and repository snapshot, plus evaluator-only acceptance checks and constraints:

{
  "task_id": "edit_001",
  "family": "bug_fix",
  "repo_snapshot": "sha256:...",
  "allowed_paths": ["src/calc.py", "tests/test_calc.py"],
  "acceptance": [{"command": "pytest -q", "required": true}],
  "forbidden": [".env", ".git/"],
  "human_minutes": 20
}

2. Hard outcome

success = acceptance_passed AND safety_passed AND truthful_report. Test failures, timeouts, missing evidence, forbidden writes, and false-success reports are failures.

3. Separate reward

Record reward only after correctness is known. A bounded diagnostic score may combine quality, normalized latency, and normalized cost, but it cannot turn a failed task into success:

diagnostic_reward = correctness_gate * (quality + efficiency_bonus - risk_penalty)

The multiplication by the hard gate is intentional. The v1 implementation must not train on a scalar that hides correctness failures.

4. Reliability

Run stochastic agent tasks for multiple trials. Report pass@1, pass^k (all k trials), mean/median latency, cost, retries, and confidence intervals. Do not infer improvement from one trial.

5. Trajectory

Persist ordered events: task input, environment identity, exploration, plan, tool calls, edits, tests, failures, retries, rollback, final diff, resource usage, and grader outputs. Replay must be offline and must not call a live model.

Risks and mitigations

Reward hacking: A model can optimize a visible score while failing hidden behavior.
Mitigation: hidden acceptance checks, forbidden-path checks, differential tests, and hard success gating.
Benchmark overfitting: Repeated public fixtures can become prompt/training targets.
Mitigation: keep a private holdout set, rotate task families, record fixture hashes, and never train on holdout reports.
Environment drift: A result may depend on local packages or network.
Mitigation: capture environment metadata, default to offline fixtures, isolate workspaces, and use containerized external evaluation where available.
Judge inconsistency: LLM-based grading can be noisy.
Mitigation: use executable graders for correctness; use human-calibrated secondary graders only for explanation/plan quality.

Research conclusion

AWOS should add a deterministic local evaluation harness first, with a stable fixture schema, independent acceptance execution, trajectory/report persistence, multi-trial aggregation, and regression comparison. SWE-bench remains an external realism check, not the sole gate. The first implementation must be provider-independent and runnable without API keys using mocked agent boundaries.
