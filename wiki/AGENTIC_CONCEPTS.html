1. Agent Architectures

An agent architecture defines the loop through which an agent perceives, reasons, and acts. Architecture choice is the highest-leverage decision in any agentic project — it determines blast radius, debuggability, and the ceiling for autonomous capability.

1.1 ReAct (Reason + Act)

Pattern: Interleave Thought → Action → Observation in a single context window. Each step is visible in the trace.

Thought: I need to look up the current error.
Action:  search_files("ImportError transformers")
Obs:     found in train.py:42
Thought: The import is wrong. I'll fix it.
Action:  replace_string_in_file(...)
When to useDefault for single-agent task execution. ≤10 tool calls.
Failure modeContext grows linearly; quality degrades on long chains.
AWOS ruleTraces exceeding 5 tool calls must be checkpointed.

1.2 Plan-and-Execute

Pattern: Separate the planner (creates a full task graph upfront) from the executor (runs each step). Maps directly onto the Research → Spec → Task triad.

Planner → [step1, step2, step3, step4]
              ↓          ↓
         Executor1   Executor2  (parallel where independent)
When to useLong-horizon tasks where upfront structure is knowable.
Failure modePlanner assumptions go stale mid-execution if environment changes.
MitigationExecutor reports back to planner after each step. Planner re-evaluates on failure.

1.3 Reflexion

Pattern: After each attempt, the agent writes a textual self-critique of what went wrong and why, then retries with that critique prepended. Critique accumulates as episodic memory of failure.

Attempt 1 → fail
Reflection: "I called the wrong tool because I confused X with Y."
Attempt 2 (with reflection prepended) → improved
AWOS mapping: Operationalised by the DEBUG_PROTOCOL two-failed-attempt rule. The debug log IS the reflexion memory. Limit to 3 cycles before escalating to human.

1.4 LATS (Language Agent Tree Search)

Pattern: Monte Carlo Tree Search over the action space. At each node, generate k candidate actions, evaluate with a value function, and continue the most promising path.

State S
├── Action A1 → S1 (value: 0.8)
├── Action A2 → S2 (value: 0.3)  ← pruned
└── Action A3 → S3 (value: 0.6)
       └── Action A4 → S4 (value: 0.9)  ← best path
Compute note (P1): LATS with k=5, depth=4 = 625 LLM calls. Never run locally. Push to Kaggle or cloud.

1.5 Critic-Actor

Pattern: Two roles — Actor generates output; Critic scores and provides structured feedback. Actor revises. Neither role bleeds into the other.

Actor → draft output
Critic → {score: 0.4, issues: ["missing error handling"], edits: [...]}
Actor → revised output
Critic → {score: 0.9, issues: []}  → accept

1.6 Self-Ask

Pattern: Decompose a complex question into explicit sub-questions, answer each, then use those answers for the main question.

Q: "Best architecture for this RL task?"
Sub-Q1: "Continuous or discrete state?" → continuous
Sub-Q2: "Sparse reward?" → yes
Sub-Q3: "Sample efficiency needed?" → high
Final:  "SAC with PER given continuous+sparse+high-efficiency"

2. Tool Use Patterns

2.1 Tool Result Envelope

Every tool call must return a conforming envelope. Non-conforming results must be normalised before the agent processes them.

{
  "success": bool,
  "text":    str,          // human-readable summary
  "data":    dict,         // structured output for downstream
  "error":   str | None,   // if success=False
  "latency_ms": float
}

2.2 Tool Chaining

Output of T1 becomes input to T2. Each link must be independently inspectable.

file_search("train.py")            → ["/src/train.py"]
                                          ↓
read_file("/src/train.py", 40, 60) → code block
                                          ↓
grep_search("ImportError")         → line 42
Rules: Never pass raw tool output to the next tool without inspecting it. If any link returns success=False, abort the chain — do not continue with partial data. Document chains longer than 3 hops in the task file.

2.3 Tool Selection Heuristics

SignalUseAvoid
Know exact filenamefile_searchgrep_search
Know exact stringgrep_searchsemantic_search
Conceptual/contextualsemantic_searchgrep_search
Reading large file sectionsSingle large read_fileMany small reads
Executing commandsexecution_subagentrun_in_terminal (unless full output needed)

2.4 Tool Error Recovery

Tool call
    ↓
success=False?
    ├── Retry 1: check parameters (path, encoding, permissions)
    ├── Retry 2: alternative tool or approach
    └── Retry 3: STOP — invoke DEBUG_PROTOCOL §Step 0
ErrorRoot causeFix
File not foundWrong relative vs absolute pathAlways use absolute paths
Regex no matchEscape issue or casingTest regex in isolation first
Subprocess timeoutBlocking on stdinAdd --no-interactive flag
API rate limitToo many parallel callsSerialize; retry with backoff

2.5 Idempotent Tool Design

Tools that modify state MUST be idempotent. Non-idempotent tools must use check-before-write:

if not already_exists(target):
    write(target)

2.6 Tool Registry Discipline

  • Register every tool with: name, description, parameters, return envelope.
  • Two tools with overlapping descriptions cause the agent to guess. Resolve at registration time.
  • Tools are dispatched through the registry — never called by raw name string.

3. Memory Systems

3.1 Working Memory

The current context window — everything the agent "has in mind" right now. Finite (typically 8K–200K tokens). Lifespan: one session.

Rules: Working memory is the most expensive resource. Summarise before appending. A 2000-token observation should become a 100-token structured note unless raw fidelity is required. Prune at every context boundary.

3.2 Episodic Memory

Immutable timestamped log of events — what happened, when. Lifespan: persists across sessions, never edited.

AWOS canonical files: docs/memory/checkpoint_YYYY-MM-DD.html, docs/debug_log.md

  • Write after the event, not before.
  • Include: what changed, what failed, what decision was made, confidence level.

3.3 Semantic Memory

Named, structured facts the agent knows — project architecture, API shapes, known-good patterns. Long-lived; updated when facts change.

AWOS canonical files: memories/repo/project_structure.md, docs/kaggle_runbook.md

  • Each fact has one canonical home (Single-Owner Rule).
  • Facts carry confidence: verified / inferred / uncertain.
  • Do not promote inferred to verified without evidence from at least one successful run.
  • Stale semantic memory is worse than no memory. Review facts after every significant failure.

3.4 Procedural Memory

Numbered, atomic, executable step-by-step instructions for recurring tasks. Long-lived; updated when the procedure changes.

AWOS canonical files: protocols/*.md, docs/<platform>_runbook.md

Rule: "Do the usual thing" is not a procedure. Write out exact commands. When a procedure breaks, update it in the same session. A silent-fail procedure is more dangerous than no procedure.

3.5 Memory Decision Table

4. Reasoning Patterns

4.1 Chain-of-Thought (CoT)

Write step-by-step reasoning before producing the final answer. Each intermediate step is explicit and inspectable.

Step 1: Error says "CUDA out of memory."
Step 2: Batch=32, embed=768, seq=512 → ~50 MB per layer × 12 layers ≈ 600 MB.
Step 3: GTX 1650 has 4 GB VRAM. Something else is resident.
Step 4: Check if model is loaded twice.
AWOS rule: Decisions that required multi-step reasoning must be checkpointed (Write-Gate). Reasoning that lives only in context is lost at session end.

4.2 Tree-of-Thought (ToT)

At each reasoning step, generate multiple candidate thoughts, evaluate, continue only the most promising. Cost: O(kd). Use selectively for high-stakes design decisions.

Problem
├── Approach A: gradient-based  → likely slow (sparse reward)
├── Approach B: evolutionary    → high variance  ← pruned
└── Approach C: model-based     → justified by data volume  ← continue
        ├── C1: MBPO    → well-studied
        └── C2: Dreamer → more sample-efficient  ← continue

4.3 Scratchpad

Persistent working notes the agent can freely read/write during a task. Separate from the final output. Allows temporary state without bloating the main context.

[SCRATCHPAD]
- tried grep for "ImportError" → found in 3 files
- train.py:42 is main suspect (direct import, no try/except)
- requirements.txt: transformers==4.28 but code uses 4.35 API
- hypothesis: version mismatch
[/SCRATCHPAD]

AWOS mapping: Session memory files (/memories/session/) act as the scratchpad. Write-Gate applies: if it's important, it moves to a real file before session end.

4.4 Least-to-Most Prompting

Decompose a hard problem into subproblems ordered from easiest to hardest. Solve each, use answers as context for harder ones. Easier subproblems are solved without error, providing reliable anchors.

4.5 Self-Consistency

Generate N independent reasoning traces for the same problem (temperature > 0), take the majority answer. Filters out errors that affect single traces. Use N=3 minimum, N=5 for critical decisions.

Failure mode: All traces make the same systematic error. Only effective when errors are random, not correlated.

5. Evaluation & Self-Improvement

5.1 Reward Signal Taxonomy

TypeDefinitionExample
SparseSignal only at episode endPass/fail on test suite
DenseSignal at every stepCoverage delta per line changed
ShapedSparse + hand-designed intermediate rewardsPartial credit for correct imports
LearnedReward model from human preferencesRLHF preference score
IntrinsicAgent-generated (curiosity, novelty)Prediction error of world model
Selection rule: Use the sparsest signal that produces stable learning. Dense/shaped rewards introduce bias; their design errors compound. Only add density when the sparse signal is too noisy to learn from.

5.2 Critic-Actor Loop (Operational)

  1. Critic must score before Actor revises. Actor never self-approves.
  2. Critic feedback must be structured: {score: float, blocking_issues: list, suggestions: list}.
  3. Score threshold before accept. Define in the spec, not at runtime. Default: score ≥ 0.8, zero blocking issues.
  4. Maximum 3 revision cycles. If score does not improve after 3 cycles, the problem is the task spec — escalate.

5.3 Self-Reflection Protocol

Trigger: After any significant failure (test regression, kernel crash, reward collapse).

  1. Write the failure state as a concrete observation (exact error, exact metric drop).
  2. List hypotheses in order of prior probability.
  3. For each hypothesis: what evidence would confirm or deny it?
  4. Gather that evidence using the narrowest tool available.
  5. Update beliefs. Write a finding. Only then write a fix.

This is DEBUG_PROTOCOL §Steps 1–4. Do not skip steps.

5.4 Evaluation Gates

Stage N training → eval gate → pass? → Stage N+1
                                  ↓ fail
                            Diagnosis + fix → retry Stage N
  • Gates defined in the spec before training begins, never adjusted after seeing results.
  • Gate criteria must be falsifiable and reproducible (same data split, same metric).
  • A gate that never fails is not a gate — raise the bar.

5.5 Ratchet State

A persisted record of the best-known metric that blocks any checkpoint regressing it.

if new_score > ratchet_state["best_score"]:
    save_checkpoint()
    ratchet_state["best_score"] = new_score
else:
    discard_checkpoint()
    log("regression — not saving")

Canonical file: data/ratchet_state.json. This is semantic memory — update after every successful training run.

5.6 Reward Shaping Safety Rules

  1. Document every shaping term with the intended behaviour it induces.
  2. Run ablation: verify the model learns the right behaviour without the term before adding it.
  3. Monitor for reward hacking: sample trajectories periodically and verify high-reward behaviour is actually desired.
  4. Shaping term budget: no more than 3 auxiliary terms in production. More terms = more interaction effects = harder to debug.

6. Multi-Agent Patterns

6.1 Orchestrator-Worker

One orchestrator manages the task plan and dispatches subtasks to stateless workers. All state flows through the orchestrator — workers never communicate directly.

Orchestrator
├── Worker A: "fetch and preprocess data"   → structured output
├── Worker B: "run training experiment"     → metrics
└── Worker C: "write evaluation report"     → depends on A+B outputs
Rules: Each worker receives a self-contained task with all required context inline. Orchestrator validates worker output before passing it downstream.

6.2 Debate / Adversarial Review

Two agents take opposing stances. A third (judge) evaluates and verdicts.

Agent A (proposer): "We should use LoRA rank 16."
Agent B (critic):   "Rank 16 too large — overfitting risk."
Agent A (rebuttal): "Validation curve shows no overfitting to epoch 8."
Judge:              "Agent A's rebuttal supported. Proceed with rank 16, monitor epoch 4."
Cost: 3x single-agent minimum. Reserve for genuinely contested decisions. Force adversarial stance explicitly — agents default to safe centrism.

6.3 Role Specialisation

RoleResponsibility
PlannerBreaks down goals into steps
ResearcherGathers external knowledge; writes research docs
ImplementerWrites code from specs
TesterWrites and runs tests; reports regressions
AuditorReviews for security, correctness, style violations
ArchivistMaintains memory files; writes checkpoints
AWOS rule: Roles must be defined in the project spec. Agents without explicit roles drift into doing everything, which means doing nothing well.

6.4 Shared Memory vs Message Passing

MechanismUse whenRisk
Shared file-based memoryAgents run sequentially or with lockingRace conditions if parallel
Message queueAgents run in parallel, asyncMessage ordering bugs
Direct prompt injectionOrchestrator passes context inlineContext bloat

Default for AWOS projects: Shared file-based memory (canonical files) with sequential agent execution.

7. Context Window Management

The context window is the agent's working memory. It is finite, ordered, and read left-to-right. Managing it well is the difference between an agent that degrades on long tasks and one that does not.

7.1 Context Budget Framework

Total budget = C tokens
├── System prompt:        ~500–2000   (fixed)
├── Task instructions:    ~500–1000   (per task)
├── Retrieved knowledge:  ~2000–5000  (variable — MUST be controlled)
├── Tool results:         ~1000–3000  (per call — MUST be compressed)
├── Reasoning trace:      ~1000–4000  (grows — MUST be pruned)
└── Output buffer:        ~500–2000   (reserve)
Rule: If any single tool result exceeds 1000 tokens, compress it before appending. If the reasoning trace exceeds 3000 tokens, summarise the oldest turns.

7.2 Chunking Strategies

StrategyWhen to use
Fixed-size (N tokens)Logs, raw data, uniform text
Semantic (paragraph/section)Structured docs, code files
Hierarchical (summary + detail)Long docs where only sections are relevant
Sliding window with overlapWhen context continuity across chunks matters
Rule: Chunk at semantic boundaries — never split code mid-function.

7.3 Summarisation Levels

LevelOutput sizeUse
Headline1 sentenceStatus update, log entry
Structured5–10 bullet pointsCheckpoint entry, step completion
Compressed transcript20–50% of originalMulti-turn history compression

7.4 Retrieval (RAG Pattern)

Step context (query) → retriever → top-K chunks → inject into prompt
  • Retrieve lazily — only when the current step actually needs external knowledge.
  • Re-rank by relevance to the specific sub-question, not the full task.
  • Never inject retrieved text verbatim if it exceeds 500 tokens — summarise first.
  • Log what was retrieved and why in the task file.

7.5 Anti-Patterns

Anti-patternProblem
Keeping all raw tool outputsContext exhaustion by step 8
Summarising too aggressively earlyLosing details needed 3 steps later
Re-reading the same file repeatedlyContext pollution; use caching
Injecting entire project historyAgent attends to irrelevant prior sessions

8. Task Decomposition Strategies

8.1 Why Decomposition Matters

A task that cannot be broken down is either trivially small or dangerously undefined. Decomposition creates verifiable intermediate states — each sub-task is a hypothesis about the path to the goal.

8.2 Hierarchical Decomposition

Goal: "Train entity AI to score > 0.8 on holdout"
├── Stage 1: Data pipeline working
│   ├── Task 1.1: SFT dataset loads without error
│   └── Task 1.2: DPO dataset has correct schema
├── Stage 2: SFT baseline trained
│   ├── Task 2.1: Loss < 1.5 at epoch 5
│   └── Task 2.2: Eval gate passes (perplexity < 20)
└── Stage 3: RL fine-tuning

AWOS rule: The Research → Spec → Task triad IS hierarchical decomposition. Spec = Stage level. Task file = Atomic level.

8.3 DAG-Based Decomposition

A ──┐
    ├──→ C ──→ E  (critical path)
B ──┘         ↑
              D   (parallel with A+B+C)
  • Draw the DAG before assigning to workers.
  • Critical path determines minimum wall-clock time regardless of parallelism.
  • Any underspecified step on the critical path blocks the entire downstream.

8.4 Iterative Refinement

Iteration 0: working naive implementation   (correctness gate)
Iteration 1: correct but slow               (performance gate)
Iteration 2: fast but high memory           (memory gate)
Iteration 3: balanced → accept
Rule: Define what "done" means for each iteration before starting it. Iterative refinement without exit conditions is an infinite loop.

8.5 Decomposition Anti-Patterns

Anti-patternProblemFix
Steps that contain "and"Two things tested as oneSplit at "and"
Steps without exit conditionsNo way to know they're completeAdd falsifiable criterion
Steps that depend on unresolved ambiguityBlocks at implementationResolve in research phase
Parallelising sequential dependenciesData race / incorrect outputDraw the DAG first
Single mega-step for complex logicUntestable, irreversibleDecompose until atomic

8.6 Atomic Step Test (Quick Reference)

Apply these 3 tests before executing any step:

  1. One-line test: "Can I write a one-sentence test that proves this step succeeded?" → If no: break it down.
  2. "And" test: Does the description contain the word "and"? → If yes: split it.
  3. Revert test: "Can I undo this step independently if wrong?" → If no: add a backup/checkpoint first.
